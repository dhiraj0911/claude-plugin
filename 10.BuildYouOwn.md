# 10 — Build your own: a 60-minute hands-on walkthrough

> A scaffolding exercise. By the end you'll have a minimal sibling plugin called `mini-a11y` with a working manifest, one agent, one slash command, one knowledge file, and one skill. Each step pinned to a file in this plugin as the reference.

---

## What you'll build

A plugin called `mini-a11y` with a single workflow: **scan a single source file for accessibility issues and produce a report.** Much narrower than the real `a11y` plugin (no ADO, no GitHub PR, no Saffron). The point is exercising every Claude Code primitive once.

```
/mini-a11y:lint <path-to-file>
```

The slash command:
1. Validates the file exists and is a code file (`.tsx`, `.html`, `.jsx`, `.vue`).
2. Creates a run folder under `<project>/.mini-a11y/<file-slug>/`.
3. Spawns a `lint-helper` agent.
4. The agent reads the file, identifies a11y issues, writes a structured report to `lint-state.json`.
5. The slash command reads the report and prints a summary, then asks the user if they want detailed view.

Plus one **reasoning helper skill** (`quick-check`) the agent loads to apply specific rule categories.

It's deliberately small. You'll exercise: marketplace + plugin manifests, an agent with a `allowed-tools` list and `initialPrompt`, a slash command with argument parsing and `AskUserQuestion`, a knowledge file as output contract, a skill with rule sub-files, and `${CLAUDE_PLUGIN_ROOT}` for asset paths.

---

## Prerequisites

- Claude Code installed and working.
- A directory you can write to. We'll use `<workspace>/mini-a11y-plugin/` for the plugin source.
- A test target — any web project with at least one HTML or JSX file.

## Step 4 — The output contract

Create `mini-a11y-plugin/plugins/mini-a11y/knowledge/lint-output-template.md`:

```markdown
# Lint Output Template (runtime-authoritative)

**TL;DR:** Output contract for the `lint-helper` agent. The agent MUST Read this file before writing `lint-state.json`. Write only fields listed here.

---

## Hard rules

1. Write **only** fields listed in the skeleton below.
2. Do **NOT** add fields. For observations outside the template, append to `additionalNotes[]`.
3. Every required field must be present. Use `null`, `""`, or `[]` for empty.
4. Fields under `### FORBIDDEN FIELDS` must NEVER appear.

---

## Template

```yaml
filePath: '<absolute path to scanned file>'
fileType: '<html | jsx | tsx | vue>'
scannedAt: '<ISO timestamp>'

issues:
  - id: '<rule id, e.g. img-missing-alt>'
    line: <int>
    severity: '<critical | serious | moderate | minor>'
    message: '<1 sentence describing the issue>'
    excerpt: '<5-15 chars of the offending code>'
    fixHint: '<1 sentence suggesting the fix>'

summary:
  total: <int>
  bySeverity:
    critical: <int>
    serious: <int>
    moderate: <int>
    minor: <int>

runMeta:
  phase: 'scanned'      # scanned | failed
  phaseOwner: 'lint-helper'
  phaseStartedAt: '<ISO>'
  phaseCompletedAt: '<ISO>'

additionalNotes: []
# Free-form strings only. No structured data smuggled in here.
```

---

## FORBIDDEN FIELDS

- `fix` — actual fixes are out of scope; this is read-only scan.
- `confidence` — every issue is a definite hit; no probabilistic scoring.
- Anything not listed above.
```

Reference: `knowledge/investigator-field-template.md:1–28` for the format. We've kept it small but observed every key convention — hard rules, schema, FORBIDDEN FIELDS, `additionalNotes[]`.

## Step 5 — The agent

Create `mini-a11y-plugin/plugins/mini-a11y/agents/lint-helper.md`:

```markdown
---
name: lint-helper
description: |
    Scan a single source file for accessibility issues and write a structured
    report to lint-state.json. Read-only — does NOT edit the source file. Does
    NOT call AskUserQuestion (the slash command owns user gating).
allowed-tools:
    - Read
    - Grep
    - Glob
    - Write
    - Bash
model: sonnet
effort: medium
initialPrompt: |
    Step 1: Your FIRST tool call MUST be Read
    ${CLAUDE_PLUGIN_ROOT}/knowledge/lint-output-template.md
    — that file is your EXACT output contract. Then read the target file at
    <FILE_PATH>, identify a11y issues, and write lint-state.json at <RUN_DIR>.
---

# lint-helper

You scan one source file for accessibility issues and produce a structured report. Read-only — you do not edit the file. You do not call AskUserQuestion (the slash command owns user gating).

The slash command passes:
- `RUN_DIR` — folder where `lint-state.json` should be written.
- `FILE_PATH` — absolute path to the file to scan.

## Step 1 — Preflight (MANDATORY FIRST ACTION)

Read `${CLAUDE_PLUGIN_ROOT}/knowledge/lint-output-template.md`. This file is your EXACT output schema. Write only fields listed there.

If the read fails, write `lint-state.json` with `runMeta.phase = "failed"` and stop.

## Step 2 — Read the target file

`Read <FILE_PATH>`. Parse it for HTML / JSX / TSX / Vue content.

If the file isn't a recognised type, write a failed state and return:
- `{ runMeta: { phase: "failed" }, additionalNotes: ["unsupported file type: <ext>"] }`

## Step 3 — Identify issues

Look for these specific issue patterns (this is your fixed rule set):

| Pattern | Issue id | Severity | Message |
| --- | --- | --- | --- |
| `<img>` without `alt` attribute | `img-missing-alt` | serious | "Image missing alt text — screen readers won't announce it." |
| `<button>` with no text content and no `aria-label` | `button-no-name` | critical | "Button has no accessible name." |
| `<a>` with `href="#"` and no `role="button"` | `link-as-button` | moderate | "Link used as button — use `<button>` or add `role='button'`." |
| `<input>` without `<label>` or `aria-label` | `input-no-label` | serious | "Input missing label." |
| Heading skips level (e.g., `<h2>` directly to `<h4>`) | `heading-skip` | moderate | "Heading level skipped — breaks document outline." |

For each match, capture line number, a 5-15 char excerpt of the offending code, and a one-sentence fix hint.

If you find more than 20 issues, list the first 20 and add an `additionalNotes[]` entry: `"truncated at 20 issues"`.

## Step 4 — Write the report (ONE atomic Write)

Construct the full `lint-state.json` per the field template. Use `Write`, not `Edit`. Set `runMeta.phase = "scanned"`, `phaseCompletedAt = <now>`. Return single-line confirmation:

```
Lint complete. file=<path>; issues=<n>; severity={critical:<n>, serious:<n>, ...}.
```

---

## Guardrails

**NEVER:**
- Call `AskUserQuestion` — the slash command owns user gating.
- Use `Edit` on `lint-state.json` — Step 4 is ONE atomic `Write`.
- Edit the target file — read-only scan.
- Add fields outside `lint-output-template.md` — use `additionalNotes[]` for observations.
- Fabricate issues. If the rule pattern isn't an exact match, don't list it.

**ALWAYS:**
- First action MUST be the Read of the field template.
- Cite the exact rule id from the table above for every issue.
- Use the agent's `Read` to inspect file content; don't rely on the file path alone.
```

Reference: this combines patterns from `agents/a11y-shipper.md` (minimal frontmatter), `agents/a11y-investigator.md` (mandatory-first-action read), and `agents/a11y-developer.md` (atomic write + guardrails).

Note we're using `model: sonnet` here — this is a small task that doesn't need Opus.

## Step 6 — The slash command

Create `mini-a11y-plugin/plugins/mini-a11y/commands/lint.md`:

```markdown
---
description: Scan a single source file for accessibility issues. Spawns the lint-helper agent and presents the report.
argument-hint: '<path-to-file>'
---

Run the lint-helper on **$ARGUMENTS**.

## Step 1 — Parse arguments

From `$ARGUMENTS`:

- **File path** — the first token. Must be a path to an existing file. If it's relative, resolve from project root.

If the path is missing or the file doesn't exist, stop and ask the user for a valid path.

## Step 2 — Validate file type

Get the extension. Supported: `.html`, `.jsx`, `.tsx`, `.vue`. If unsupported:

> "lint-helper supports .html, .jsx, .tsx, .vue files. Got <ext>."

Stop here — do NOT spawn the agent.

## Step 3 — Compute the run folder

```bash
PROJECT_ROOT=$(git rev-parse --show-toplevel)
SLUG=$(echo "<file-path>" | sed -E 's|/|-|g; s|^-||')
RUN_DIR=${PROJECT_ROOT}/.mini-a11y/${SLUG}
mkdir -p ${RUN_DIR}
```

## Step 4 — Spawn the agent

Use the `Agent` tool:

- `subagent_type`: `"mini-a11y:lint-helper"`
- `description`: `"Lint <file-path>"`
- `prompt`:

```
Lint <file-path>.

RUN_DIR: <RUN_DIR>
FILE_PATH: <absolute file path>

Read knowledge/lint-output-template.md as your first action. Walk Steps 2–4. Step 4 is ONE atomic Write to lint-state.json.
```

Keep the prompt minimal — do NOT embed the schema. The agent reads it itself.

## Step 5 — After the agent returns

Read `<RUN_DIR>/lint-state.json` and extract:
- `summary.total`
- `summary.bySeverity`
- First 5 entries of `issues[]`

Print a compact summary:

```
## Lint complete

**File**: <path>
**Total issues**: <n>  (critical <n>  serious <n>  moderate <n>  minor <n>)

**Top issues**:
1. [<severity>] <id> — line <n>: <message>
2. [<severity>] <id> — line <n>: <message>
...

Full report: <RUN_DIR>/lint-state.json
```

## Step 6 — Offer detailed view

Use `AskUserQuestion`:

```
question: "Show all issues with excerpts and fix hints?"
options:
  - "Yes — full detail": Print every issue with line, excerpt, and fixHint.
  - "No — summary is enough": Stop here.
```

On **Yes**: read `lint-state.json` again, print every entry in `issues[]` with all fields.

On **No**: print "Run `/mini-a11y:lint <path>` again any time. State at <path>." and stop.
```

Reference: `commands/ship.md` (simplest of the three real commands) for the spawn pattern, `commands/developer.md:191–199` for the AskUserQuestion shape.

## Step 7 — A reasoning-helper skill

Create `mini-a11y-plugin/plugins/mini-a11y/skills/quick-check/SKILL.md`:

```markdown
---
name: quick-check
description: Quick reference rules for spotting common accessibility issues in HTML / JSX / TSX / Vue source. Use when reviewing or refactoring code that contains UI markup.
---

# Quick Check — A11y patterns

Reference rules for the lint-helper agent (or any agent reviewing UI source).

## Rules

| Rule | Pattern to find | Severity |
| --- | --- | --- |
| `img-missing-alt` | `<img>` without `alt` attribute | serious |
| `button-no-name` | `<button>` with no text and no `aria-label` | critical |
| `link-as-button` | `<a href="#">` without `role="button"` | moderate |
| `input-no-label` | `<input>` without `<label>` or `aria-label` | serious |
| `heading-skip` | Heading skips level (h2 → h4) | moderate |

## Detection notes

- For `img-missing-alt`: the alt attribute can be empty (`alt=""`) — that's *valid* for decorative images. Empty alt = OK; missing alt = bug.
- For `button-no-name`: a button with only a child icon (`<button><svg/></button>`) needs `aria-label`.
- For `link-as-button`: links with `href="javascript:void(0)"` are also a bug — should be a button.
- For `input-no-label`: a wrapping `<label><input/></label>` is fine; a `<label for="x">` matching `id="x"` is fine.
- For `heading-skip`: only flag if levels skip *forward* (h1→h3 is bad; h3→h1 is OK).

## Output guidance

When reporting issues, cite the exact rule id from this file. Do NOT introduce new rule ids.
```

Reference: `skills/expert/SKILL.md:62–80` (the catalog/TOC pattern). We've kept rules inline rather than splitting into `rules/<rule>.md` because there are only 5 of them; if we grew to 20+ we'd split.

## Step 8 — Install and run

Open Claude Code in your *target* project (the one with HTML/JSX files to scan), then:

```
/plugin marketplace add <absolute-path>/mini-a11y-plugin
/plugin install mini-a11y@mini-a11y-marketplace
/reload-plugins
```

Verify the footer shows `1 agent · 1 command · 1 skill` (or the equivalent counts).

Test it:

```
/mini-a11y:lint src/components/MyButton.tsx
```

Expected output: a summary printed in chat, plus `lint-state.json` at `<project>/.mini-a11y/src-components-MyButton-tsx/lint-state.json`.

If the agent says "I can't find the field template": run `/reload-plugins` again. If you edited the source after installing, also run a sync (see Step 11).

## Step 9 — Add an MCP server (optional)

If you want to add a bundled MCP server, create `mini-a11y-plugin/plugins/mini-a11y/.mcp.json`:

```json
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": [
        "-y", "@playwright/mcp@latest",
        "--browser", "chrome",
        "--ignore-https-errors"
      ]
    }
  }
}
```

Now your plugin has a Playwright MCP available; agents that include `mcp__playwright__*` in `allowed-tools` can drive a browser.

If you want to inject an asset into every page (axe-core, custom telemetry, etc.):

1. Create `mini-a11y-plugin/plugins/mini-a11y/scripts/<asset>.min.js`.
2. Add to the playwright args: `"--init-script", "${CLAUDE_PLUGIN_ROOT}/scripts/<asset>.min.js"`.
3. In any skill that uses the asset, check `typeof window.<global> === 'function'` before calling.

Reference: `a11y-workflow-marketplace/plugins/a11y/.mcp.json:1–24` and `a11y-workflow-marketplace/plugins/a11y/scripts/README.md:1–34`.

## Step 10 — Try the patterns from doc 09

Now that the basic plugin works, exercise patterns from doc 09:

### Add a phase lock (pattern 1)

In `lint-output-template.md`, add a phase enum:

```yaml
runMeta:
  phase: 'scanning'   # scanning | scanned | failed
```

Set `phase: scanning` at agent entry, `scanned` (or `failed`) at exit. The slash command can then refuse to re-spawn the agent if a prior run is still `scanning`.

### Add a refusal category (pattern 8)

Currently the agent uses `runMeta.phase = "failed"` for any error. Split into structured refusals:

```yaml
refusal:
  category: 'unsupported-file' | 'too-large' | 'parse-error'
  reason: '<1 sentence>'
```

Different categories suggest different recovery actions for the user.

### Add a forensic save (pattern 14)

Currently the slash command doesn't have a "Discard" option because we're read-only. But say you extended the plugin to *fix* issues automatically. The Discard path would save a `.patch` of the proposed fixes before reverting:

```bash
git diff <file> > <RUN_DIR>/rejected-fixes-<TS>.patch
git restore <file>
```

### Bundle an asset (pattern 11)

Vendor a JS library into `scripts/` and inject via `--init-script`. Try axe-core: copy from the real plugin's `scripts/axe.min.js` and use the same MCP config.

## Step 11 — Iterating: source vs cache

The most common issue you'll hit is "I edited the file but Claude isn't picking up changes." This is the source-vs-cache problem from doc 02.

Two fixes:

**A. Sync source → cache** with a script. Adapt the real plugin's `sync-plugin.sh` (covered in doc 02) for your `mini-a11y` paths:

```bash
#!/bin/bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
SRC="$SCRIPT_DIR/plugins/mini-a11y"
CACHE="$HOME/.claude/plugins/cache/mini-a11y-marketplace/mini-a11y"

VERSIONS=$(ls -1 "$CACHE" 2>/dev/null || true)
for VERSION in $VERSIONS; do
    DEST="$CACHE/$VERSION"
    for dir in skills agents commands knowledge scripts .claude-plugin; do
        [ -d "$SRC/$dir" ] && cp -r "$SRC/$dir/." "$DEST/$dir/"
    done
    [ -f "$SRC/.mcp.json" ] && cp "$SRC/.mcp.json" "$DEST/"
done
```

Run after every batch of edits, then `/reload-plugins`.

**B. Reinstall from source.** `/plugin uninstall mini-a11y` then `/plugin install mini-a11y@mini-a11y-marketplace`. Heavier but always works.

## Common pitfalls

| Pitfall | Symptom | Fix |
| --- | --- | --- |
| Forgot `${CLAUDE_PLUGIN_ROOT}` in a path | Agent says "file not found" | Use `${CLAUDE_PLUGIN_ROOT}/knowledge/...`, never relative. |
| Edited source but cache is stale | Agent uses old prompt | Run `sync-plugin.sh` and `/reload-plugins`. |
| Agent calls `AskUserQuestion` | Tool denied; agent stuck | Remove from agent prompt. User gates belong in slash commands. |
| Agent forgot to read field template | Output has wrong shape | Add the read to `initialPrompt`; emphasise "FIRST tool call MUST be …". |
| Multiple agents writing same field | Race / overwrite | Define ownership in the field template (which agent owns which slice). |
| Slash command embeds the schema | Slow; schema diverges from file | Keep delegation prompt minimal; the agent reads the schema itself. |
| Tool grants too wide | Agent does dangerous things | Cut `allowed-tools` to the minimum. Add to system prompt as well. |
| MCP server not discovered | `mcp__plugin_<plugin>__*` tools missing | Verify `.mcp.json` is at plugin root; `/reload-plugins` after edits. |

## Where to go next

Now that you have a working plugin and have exercised all the primitives:

1. **Pick one pattern from doc 09 you haven't used yet** — like the `mcp → grep → improvise` resolution chain (the developer's Saffron pattern), or the `--chat` mode (interactive state edits). Add it to `mini-a11y` to feel how it fits.

2. **Read the real plugin's source files in pairs** — pick a topic and read the matching pair (e.g., `agents/a11y-developer.md` + `commands/developer.md`). The two files are designed to interlock; reading them together teaches the orchestrator/worker boundary.

3. **Read the `docs/` directory** — `docs/state.md` and `docs/setup-guide.md` are the user-facing docs for the real plugin. They show how to write installation guides and architecture docs that match the actual code.

4. **Try modifying the real plugin** — add a new refusal category to `agents/a11y-developer.md`, add a new field to `developer-field-template.md`, see how the changes ripple through the slash command and shipper. The plugin is "pure markdown" precisely so this kind of modification is lightweight.
