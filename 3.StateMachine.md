# 03 — The state machine: one shared file, one phase lock

> The conceptual core. Three agents collaborate by writing different slices of one JSON file. A single field — `runMeta.phase` — tells each agent whether it's allowed to run.

---

## The single shared file

Every bug gets a folder:

```
<project-root>/.a11y/a11y-runs/AB<bug-id>/
├── run-state.json         ← THE state file
├── attachments/           ← screenshots downloaded by the investigator
│   ├── image1.png
│   └── image2.png
├── reports/               ← (reserved for future use)
├── .pr-body.md            ← temp file the shipper writes for `gh pr create`
└── rejected-diff-*.patch  ← forensic diffs from Discard at the gate
```

Inside that folder, **one** JSON file is the system of record: `run-state.json`. Every agent reads it, every agent writes it. There is no other channel of communication between agents — no "pass a payload to the next agent," no in-memory message bus. If you can't see it in `run-state.json`, it didn't happen.

`docs/state.md:14–17` puts it bluntly:

> Each step writes its output to a single shared file — `<project-root>/.a11y/a11y-runs/AB<bug-id>/run-state.json` — and stops cleanly so the user can review before continuing. The next agent reads the prior agent's slice and appends its own.

This is the pattern. Let's break it down.

---

## Why this design

Alternatives the plugin *didn't* pick, and why:

| Alternative | What's wrong with it |
| --- | --- |
| **Pass a payload between agents in memory** | Crashes lose work. No audit trail. No way for the user to inspect mid-run. |
| **Have each agent write its own file (`investigation.json`, `development.json`, …)** | Now you need a file-naming convention, a way to discover which file is the latest, and merge logic when anything goes wrong. |
| **Use a real database / RPC service** | Massive overhead for a tool that runs locally on one developer's machine. Defeats the "pure markdown plugin" goal. |
| **Embed the state in the prompt and let the agent choose what to keep** | The schema becomes implicit. Two runs of "the same agent" produce subtly different output shapes. Downstream agents can't rely on field names. |

The "one file, accumulating layers" choice gives you:

- **Atomicity per phase.** Each agent does its work in working memory, then writes the entire file once at the end. Crash mid-work? The file is still in the *prior* agent's last-known-good state.
- **Resumability.** The next agent re-reads the file and picks up exactly where the prior left off. No "what was that variable called again."
- **Observability.** You (the human) can `cat run-state.json` mid-run and see exactly where the workflow is.
- **Forking-friendly.** Two parallel `/a11y:developer` runs against two different bugs each have their own state file, in their own folder. Nothing collides.

## Section ownership

The file is divided into top-level sections, and **each agent owns specific sections.** No agent rewrites a section it doesn't own. Quoted from `docs/state.md:185–195`:

| Section | Owner | Contents |
| --- | --- | --- |
| `bug.*` | investigator | Work item metadata (title, severity, ADO fields, repro steps) |
| `attachments[]` | investigator | Downloaded screenshots + AI-extracted visual analysis |
| `classification` | investigator | Product, theme, blast radius |
| `decision` | investigator | Status, gateReason, work order (targetFiles, scope, hypothesis) |
| `development` | developer (+ slash command) | Branch, files changed, approach, diff stats, self-check, diffReview |
| `shipping` | shipper | Commit SHA, PR URL, draft status |
| `runMeta.phase` | all | The phase lock |

Two consequences worth naming:

1. **Investigator-owned fields are read-only to the developer**, and vice versa. The developer agent's spec spells this out (`agents/a11y-developer.md:480`):

   > Preserve EVERY other top-level key untouched (`bug.*`, `attachments.*`, `attachmentsSummary.*`, `classification.*`, `decision.*`, `knowledgeBaseContext.*`, `blastRadius.*`, `cardinalRule`, `gitStatus.*`, `stakeholderSignals.*`, `additionalNotes[]`).

   The shipper says the same about the developer's slice (`agents/a11y-shipper.md:135`).

2. **The slash command is the only "agent" that writes the developer slice twice.** The developer agent writes once at end-of-run with `userChoices.diffReview = ""`. After the diff-review gate, the slash command writes a follow-up to fill in `userChoices.diffReview = "approved" | "discarded"` and the resulting `commit` block (or to set `revert.*` on Discard). This is unusual — usually a slice is single-writer — but it's necessary because the user gate and the agent run are separate phases. Doc 05 covers the gate flow in detail.

## The phase lock

`runMeta.phase` is a single string field whose value is the cursor position in the workflow:

```
investigating → ready-for-developer → implementing → ready-for-verify → shipping → done
                                                                                 ↘ failed
                                                                                 ↘ refused
                                                                                 ↘ aborted
```

Every agent does two things at runtime that depend on this field:

1. **Refuse if the phase is wrong.** The shipper (`agents/a11y-shipper.md:42`):

   > | Check | Failure reason |
   > | `runMeta.phase == 'ready-for-verify'` | "Phase=`<actual>`, expected `ready-for-verify`." |

   The developer (`agents/a11y-developer.md:94`):

   > | Mode | Required entry state |
   > | Bug-ID (canonical) | `runMeta.phase == "ready-for-developer"` AND `decision.status == "ready-to-proceed"` |

   If the precondition fails, the agent doesn't try to "do its best anyway." It writes a refusal slice and returns. The user can then unstick state by re-running the prior step, or by using the investigator's `--chat` mode to repair `run-state.json` directly.

2. **Update phase on entry and exit.** Every agent sets `phaseStartedAt`, `phaseOwner`, and (at the end) `phaseCompletedAt` and the next phase value. This gives `run-state.json` a wall-clock audit trail for every transition.

### Terminal states

Four ways a phase chain can end:

| Terminal | Meaning |
| --- | --- |
| `done` | Shipped — PR exists, work item is on a branch, everything in order. |
| `failed` | An agent hit a hard error it couldn't recover from (e.g., couldn't read its template, ADO returned 401). State has a `failure.reason`. |
| `refused` | An agent hit a *soft* error it deliberately stopped on (Low confidence, 15-call grep budget exhausted, design team confirmation needed). Has a structured `refusal.category` and `refusal.reason`. |
| `aborted` | The user picked **Discard** at the diff-review gate. The slash command — *not* the agent — writes this terminal state. |

The split between `failed`, `refused`, and `aborted` matters. They mean different things to the orchestrator:

- `failed` is "rare; investigate; fix the cause." Maybe a stale Azure CLI token.
- `refused` is "expected; here's structured info on what's blocking; user can address and re-run."
- `aborted` is "user said no thank you; everything is cleaned up."

Doc 04 has the full refusal taxonomy.

## Atomic single-write semantics

When the developer agent finishes a fix, it does **exactly one** `Write` call against `run-state.json`. Not three small `Edit`s, not "write the development slice now and the runMeta phase later." One write of the entire file's new contents.

`agents/a11y-developer.md:469–488` (Step 7 — Final write):

> 1. `Read <RUN_DIR>/run-state.json`.
> 2. Construct the full updated state in working memory.
> 3. **`Write <RUN_DIR>/run-state.json` with the full new content.** ONE call. Do not split into multiple Edits.

And the rule made explicit (`agents/a11y-developer.md:564–565`):

> **NEVER** Use `Edit` on `run-state.json`. Step 7 is ONE atomic `Write` of the full file. Multiple incremental Edits are forbidden — they're slow, fragile, and produce unauditable partial state.

Why this matters:

- **Crash safety.** If the LLM crashes mid-fix (rate limit, timeout, bug), `run-state.json` is still the prior agent's clean state. The user re-runs and starts over rather than dealing with a half-written record.
- **Observability.** A reader of `run-state.json` never sees a "the developer started but didn't finish" zombie record. It's either pre-developer (`phase == ready-for-developer`) or post-developer (`phase == ready-for-verify`).
- **Audit trail integrity.** A multi-Edit approach can leave the file in shapes the schema doesn't permit (a `development` slice with `status` set but `branch` not set yet). The atomic write makes "valid run-state shape" an invariant.

The shipper enforces the same rule (`agents/a11y-shipper.md:194`):

> **NEVER** Use `Edit` on `run-state.json`. Step 4 is ONE atomic `Write` of the full file.

## Worked example: tracing one bug

Let's run AB#2341709 through the whole pipeline and watch what happens to `run-state.json`.

### Phase 0 — `investigating`

User runs `/a11y:investigate 2341709`. The slash command:

1. Computes `RUN_DIR=<project>/.a11y/a11y-runs/AB2341709`.
2. Spawns the `a11y-investigator` agent with `RUN_DIR` in the prompt.

The investigator's first action is mandatory:

> Phase 0: Your FIRST tool call MUST be Read `${CLAUDE_PLUGIN_ROOT}/knowledge/investigator-field-template.md`
>
> — `agents/a11y-investigator.md:21–22`

It reads the output contract, then `mkdir`s the run folder, then writes initial state:

```jsonc
{
    "bugId": "2341709",
    "url": "<ado-url>",
    "runMeta": {
        "phase": "investigating",
        "phaseOwner": "a11y-investigator",
        "phaseStartedAt": "2026-04-29T14:01:03Z"
    }
}
```

The investigator then does its 9-phase discovery flow (ADO calls, screenshot downloads, knowledge-base greps, classification). At the end, it writes ONE final `Write` containing every populated field, with:

```jsonc
{
    "bug": { /* parsed from ADO */ },
    "attachments": [ /* with analysis */ ],
    "classification": { "product": {...}, "theme": {...} },
    "decision": {
        "status": "ready-to-proceed",
        "confidence": "High",
        "workOrder": { /* targetFiles, scope, hypothesis */ }
    },
    "runMeta": {
        "phase": "ready-for-developer",
        "phaseCompletedAt": "2026-04-29T14:04:21Z"
    }
}
```

Key transitions: `phase: investigating → ready-for-developer`. The slash command reads the file and prints a summary, then tells the user `/a11y:developer 2341709`.

### Phase 1 — `implementing`

User runs `/a11y:developer 2341709`. The slash command:

1. Validates `runMeta.phase == "ready-for-developer"` AND `decision.status == "ready-to-proceed"` (`commands/developer.md:50`).
2. Creates the fix branch: `git checkout -b fix/AB#2341709-2-5-8-target-size-link` (`commands/developer.md:79–83`).
3. Spawns the `a11y-developer` agent.

The developer's first action: parallel read of `developer-field-template.md` AND `principles.md`. Then it reads `run-state.json` and validates the phase precondition again (defense in depth — the slash command checked too, but a misconfigured environment could spawn the agent without checking).

In working memory, it sets `runMeta.phase = "implementing"` (`agents/a11y-developer.md:116`). It does *not* persist this yet — that happens at the final write only.

The agent does its 6 work steps (knowledge greps, Saffron MCP, source reads, approach, edits, self-check). At Step 7 it writes once:

```jsonc
{
    /* investigator's slices preserved EXACTLY */
    "bug": {...},
    "attachments": [...],
    "classification": {...},
    "decision": {...},

    "development": {
        "status": "ready-for-verify",
        "confidence": "High",
        "branch": "fix/AB#2341709-2-5-8-target-size-link",
        "approach": { /* summary, filesToChange, etc. */ },
        "filesChanged": { "source": [...], "tests": [...] },
        "selfCheck": {
            "ran": true,
            "targetResolved": "true",
            "lint": "pass",
            "test": "pass"
        },
        "userChoices": {
            "diffReview": ""    /* blank — slash command fills */
        },
        "commit": null,           /* blank — slash command fills */
        "consulted": { /* saffron, products, themes */ }
    },

    "runMeta": {
        "phase": "ready-for-verify",
        "phaseOwner": "a11y-developer",
        "phaseCompletedAt": "2026-04-29T14:14:38Z"
    }
}
```

The agent returns. The slash command (still running in your main session) reads the new state, runs `git diff main..HEAD`, and presents the diff with `AskUserQuestion`.

### Phase 2 — the gate (`ready-for-verify`)

You pick **Approve**. The slash command (`commands/developer.md:228–257`):

1. Stages explicit paths (`git add <each file>` — never `git add -A`).
2. Commits with `--no-verify` (Step 6 already ran lint+test).
3. Captures `git rev-parse --short HEAD`.
4. Re-reads `run-state.json` and writes ONE update:

```jsonc
{
    /* everything else preserved */
    "development": {
        /* everything else preserved */
        "userChoices": {
            "diffReview": "approved"     /* now filled */
        },
        "commit": {                       /* now filled */
            "sha": "a3f1e8b",
            "subject": "fix(a11y): assign valid target size to in-result links (AB#2341709)",
            "committedAt": "2026-04-29T14:16:02Z"
        }
    }
    /* runMeta.phase still "ready-for-verify" — phase doesn't change at gate */
}
```

Note: the slash command writes the `development` slice (a slice owned by the developer agent). This is the only documented exception to "one slice per writer." The developer agent leaves `userChoices.diffReview` and `commit` blank precisely so the slash command can fill them post-gate.

If you'd picked **Discard**, the slash command would have written `development.status = "aborted"` and `runMeta.phase = "aborted"`, plus a forensic `revert.patchPath` pointing at a saved `.patch` file. The branch would be deleted.

### Phase 3 — `shipping → done`

You run `/a11y:ship 2341709`. The slash command spawns the shipper, which:

1. Validates `runMeta.phase == "ready-for-verify"` AND `userChoices.diffReview == "approved"` AND `commit.sha` is non-empty (`agents/a11y-shipper.md:42–47`).
2. Checks idempotency — does a PR already exist for this branch? If yes, mark `already-shipped` and exit (`agents/a11y-shipper.md:59–65`).
3. Sets `runMeta.phase = "shipping"` and persists *before* the first git mutation (`agents/a11y-shipper.md:95–96`).
4. `git push -u origin <branch>`.
5. `gh pr create --draft --base main --head <branch> --title <title> --body-file .pr-body.md`.
6. Step 4 final write: appends a `shipping` slice and sets `runMeta.phase = "done"`.

```jsonc
{
    /* everything else preserved */
    "shipping": {
        "status": "shipped",
        "push": { "branch": "fix/AB#2341709-...", "pushedAt": "..." },
        "pullRequest": { "number": 8421, "url": "https://github.com/...", "isDraft": true },
        "failure": null
    },
    "runMeta": {
        "phase": "done",
        "phaseOwner": "a11y-shipper",
        "phaseCompletedAt": "..."
    }
}
```

Done. The PR is in GitHub, draft, awaiting your review-and-promote.

## Get-unstuck recipe

Phase locks are great until they aren't. If a run aborts uncleanly (network died mid-shipper, you killed Claude Code mid-developer), `phase` may be stuck at an intermediate value (`implementing`, `shipping`) and the next agent will refuse.

`docs/state.md:259–269` gives the recipe:

> 1. Open `run-state.json` and inspect `runMeta.phase`.
> 2. If you genuinely want to resume, set it to the entry state for the next agent (`ready-for-developer`, `ready-for-verify`).
> 3. Re-run the appropriate slash command.
>
> Or use `/a11y:investigate <id> --chat` to repair the state file conversationally.

The investigator's `--chat` mode is documented in doc 05; it loads `run-state.json` and the field template into the main session, lets you describe what to change in English, and the orchestrator does the JSON edits while respecting the schema.

This is the safety valve. The phase lock is enforced by *agents*, not by the harness — so the user (an actor outside the lock) can always recover by editing the file.

---

## What this pattern generalises to

The shape "one shared state file + a phase enum + per-section ownership + atomic single-write at end" is reusable any time you have:

- **More than one autonomous agent** taking turns at a single conceptual workflow.
- **A user gate or hand-off** in the middle that requires the workflow to pause and resume cleanly.
- **A need for resumability** — your agents may crash, time out, or be deliberately interrupted by the user.

You'll meet this pattern in doc 09 ("Phase lock for multi-agent state machines" and "Atomic single-write at agent end" are entries 1 and 2 of the design pattern catalog).
