# 01 — Overview: the problem and the shape of the solution

> Read this first. Everything that follows assumes you understand the *why* before the *how*.

---

## What this plugin does, in one paragraph

It takes an Azure DevOps accessibility bug — a row in a tracking system that says "this button has no accessible name on the Westlaw search page" — and turns it into a draft GitHub pull request. It does the classification, the source-code edit, the regression test, the commit, and the PR body. A human approves the diff once, in the middle. Everything else is automated.

The README puts it directly:

> Today the developer reviews each handoff and corrects what the AI gets wrong. The end state is a single command that takes a bug ID (or an ADO query) and returns a draft PR — most of the time, no human in the middle.
>
> — `README.md:11`

That is the goal. The current shipping product (v1) gets you most of the way there: three commands, run by hand, with one user gate.

---

## Why this is interesting — and why one big agent isn't enough

If you've never thought about *how* to automate a multi-step workflow with LLM agents, your first instinct is probably "give one agent the bug, tell it to fix it." That instinct breaks fast:

| Problem | What happens with one big agent |
| --- | --- |
| **Mid-task user input** — the LLM needs to ask "is this Westlaw or Westlaw Edge?" | The agent guesses (and gets it wrong half the time) or hangs waiting for input it can't ask for. |
| **Trust boundaries** — the user wants to review the diff *before* it gets pushed | The agent has to decide for itself when to stop, so it stops at the wrong moment. |
| **Parallelism** — the user wants to fix five bugs at once on five branches | One agent shape forces serialization, or branch collisions, or both. |
| **Resumability** — the LLM crashes mid-fix and you need to pick up where it stopped | The agent has no concept of "phase," so resume re-does work or skips it. |
| **Tool surface area** — investigation needs ADO MCP, fixing needs file edits, shipping needs `gh` | Granting one agent every tool means a misstep can do anything from "delete a file" to "open a PR with a placeholder body." |

The plugin's answer: **split the workflow into three agents, each with a narrow job and a narrow toolset, talking to each other through one shared state file.** The agents are pure workers. A *slash command* — which runs in your main Claude Code session — sits between you and each agent, owning user gates and git mutations.

## The shape of the solution

```
                        ┌────────────────────────────────────┐
                        │   <project>/.a11y/a11y-runs/       │
                        │     AB2341709/                     │
                        │       run-state.json   ◄──────┐    │
                        │       attachments/             │    │
                        └────────────────────────────────│────┘
                                                         │
       you type:                                         │  read + write
       ────────                                          │
       /a11y:investigate 2341709    ──spawns──►  [a11y-investigator agent]
                                                  · reads ADO MCP
                                                  · downloads screenshots
                                                  · classifies product / theme / WCAG
                                                  · writes `bug.*`, `classification`,
                                                    `decision`, `attachments[]`
       (you read the work order)
       ◄────────────────────────────────────────  returns

       /a11y:developer 2341709      ──creates branch──►
                                    ──spawns────────►  [a11y-developer agent]
                                                        · reads work order
                                                        · reviews screenshots (ground truth)
                                                        · greps source within 15-call budget
                                                        · calls Saffron MCP for design tokens
                                                        · edits source + tests
                                                        · runs lint + project tests
                                                        · writes `development.*`
                                    ◄────────────────  returns
       [diff-review GATE]   ◄── slash command shows diff and asks
       Approve / Adjust / Discard
                                    ──on Approve──► commit, record SHA in run-state

       /a11y:ship 2341709           ──spawns──►  [a11y-shipper agent]
                                                  · validates `commit.sha` exists
                                                  · drafts PR title + body from state
                                                  · pushes branch
                                                  · `gh pr create --draft`
                                                  · writes `shipping.*`
                                    ◄──────────  returns

       phase:  investigating → ready-for-developer → implementing →
               ready-for-verify → shipping → done
```

Six things are happening here. They are the patterns you will keep meeting in this codebase, so name them now:

1. **One shared file (`run-state.json`).** Every step appends a slice. No agent-to-agent messaging, no in-memory handoff, no RPC. Crash mid-run? Re-read the file.
2. **A phase lock.** `runMeta.phase` is the cursor. Each agent refuses to start if the cursor isn't on its expected entry phase.
3. **Three subagents with narrow tool grants.** The investigator can read ADO but can't `Edit` source. The developer can `Edit` source but can't `git commit`. The shipper can run `gh` but can't read ADO. Tool grants *are* the boundaries.
4. **Slash commands own user gating + git.** Subagents can't call `AskUserQuestion`, can't `git checkout`, can't push. The orchestrator (the slash command, running in your main session) does all of that.
5. **One user gate per bug.** Approve / Adjust / Discard, on the actual diff, after the agent returns.
6. **Drafts only.** PRs ship as drafts. A human still promotes to ready-for-review. The plugin makes the labor cheap; it doesn't pretend the human can step out entirely.

## How the plugin maps to Claude Code primitives

Claude Code is a CLI / IDE harness that gives you four kinds of "user-extensible artifact":

| Primitive | What it is | This plugin uses it for |
| --- | --- | --- |
| **slash command** (`commands/*.md`) | Markdown file. Runs as instructions in the main session when you type `/<name>`. Can call any tool. | The 3 orchestrators: `/a11y:investigate`, `/a11y:developer`, `/a11y:ship`. |
| **subagent** (`agents/*.md`) | Markdown file with frontmatter. Runs in an isolated sub-context when invoked via the `Agent` tool. Has its own tool allowlist. **Cannot call `AskUserQuestion`.** | The 3 workers: `a11y-investigator`, `a11y-developer`, `a11y-shipper`. |
| **skill** (`skills/<name>/SKILL.md`) | Markdown file. Loaded contextually when the user (or another piece of context) names it. Can be user-invokable as a slash command, or just a reference helper. | One user-invokable skill (`a11y-browser-verify` — Playwright + axe). Five reasoning helpers (`expert`, `lint`, `localize`, `test`, `ux`) loaded by the developer agent. |
| **MCP server** (`.mcp.json`) | Process speaking the Model Context Protocol. Exposes external tools (databases, browsers, design systems). | Four servers: `Ask Saffron MCP Server`, `playwright`, `azure-devops`, `github`. Two are bundled in the plugin's `.mcp.json`; two are at user / project level. |

The plugin isn't using anything exotic. It's using all four primitives at once, *carefully*. That's why it's a good study text.

## A word on "why this is hard"

Reading this overview, you might think: "OK — three roles, one state file, a phase enum. Not exactly rocket science." That's correct. The interesting part isn't the architecture; it's the *discipline* every artifact in the plugin practices to keep the architecture from rotting.

Examples you will meet:

- The developer agent's first action **must** be a parallel read of two markdown files. Not "should be," not "is recommended." Must. (`agents/a11y-developer.md:79–86`).
- The agent never writes `run-state.json` more than once per run, and it must use `Write` not `Edit`. Multiple `Edit` calls would be slow, fragile, and "produce unauditable partial state" — so they are *forbidden* (`agents/a11y-developer.md:564–565`).
- The investigator is forbidden from grepping the source tree. That's the developer's job. The investigator gets ADO + screenshots + the knowledge base, and that's it (`agents/a11y-investigator.md:50`).
- When the user discards a diff, the orchestrator **always** saves a `.patch` file before running `git branch -D`. Discarding work without forensics is a bug, not a feature (`commands/developer.md:283–298`).
- A developer agent that hits Low confidence is **not** allowed to "round up" to Medium. The investigator's confidence rule is the same: "Never guess. If a dimension is Low confidence, gate to the user. Do NOT pick a value and report Medium" (`agents/a11y-investigator.md:250–252`).

The hard part is naming these rules and writing them down. Once you have them, the architecture follows. Doc 09 collects them as patterns.

## Concrete anchors

Two passages from the existing repo docs you should bookmark:

**The architecture statement** (`docs/state.md:9–17`):

> The plugin orchestrates three agents sequentially against a single ADO bug:
> ```
> investigate ──► develop ──► ship
> ```
> Each step writes its output to a single shared file — `<project-root>/.a11y/a11y-runs/AB<bug-id>/run-state.json` — and stops cleanly so the user can review before continuing. The next agent reads the prior agent's slice and appends its own.

**The orchestration rule** (`docs/state.md:27`):

> **Slash commands own user gating.** The `/a11y:developer` slash command spawns its agent, then presents the resulting diff via `AskUserQuestion` with three options: Approve, Request adjustments, Discard. Agents themselves are pure workers — they do not call `AskUserQuestion`.

Internalize these two statements. The whole plugin is one or the other in disguise.
