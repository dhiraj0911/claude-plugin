# 07 — Knowledge base: separating reasoning rules from project data

> The `knowledge/` folder is the plugin's data layer — markdown files that agents grep and read at runtime. The trick is keeping four kinds of file separate, each with its own audience and its own rules.

---

## The problem this solves

You're writing a system prompt for an agent that fixes WCAG bugs. You want to teach it:

1. **A standard for output** — "your `run-state.json` must have these exact field names."
2. **Universal a11y reasoning** — "use `aria-labelledby` before `aria-label`; never duplicate native semantics."
3. **Project-specific facts** — "the Westlaw Edge product lives under `Products/Westlaw/Edge/...`."
4. **Skill-specific guides** — "when reading a screenshot, extract these fields."

If you cram all four into the system prompt, the prompt grows to 30 KB, costs money on every run, and is impossible to edit selectively. If you embed (1) and (2) in the agent file but (3) in the slash command and (4) somewhere else, you've split your knowledge across artifacts that update on different cadences.

The `knowledge/` folder is the plugin's answer: **one folder, four genres, each in its own file, each grep-friendly.**

---

## The four genres

```
plugins/a11y/knowledge/
├── README.md                          ← the conventions
├── investigator-field-template.md     ← Output contract (genre 1)
├── developer-field-template.md        ← Output contract (genre 1)
├── principles.md                      ← Universal reasoning (genre 2)
├── products.md                        ← Project-specific data (genre 3)
├── themes.md                          ← Project-specific data (genre 3)
└── attachment-analysis.md             ← Prompt guide (genre 4)
```

| Genre | Files | Owner | Edited when |
| --- | --- | --- | --- |
| **1. Output contracts** | `investigator-field-template.md`, `developer-field-template.md` | The agent that writes the slice | Schema changes (rare, schema-version-bumped) |
| **2. Universal reasoning rules** | `principles.md` | Repo-agnostic | Best practices evolve; never per-project |
| **3. Project-specific data** | `products.md`, `themes.md` | Per-codebase | Forking the plugin to a new repo |
| **4. Prompt guides** | `attachment-analysis.md` | Repo-agnostic | Image analysis methodology improves |

The README states this directly (`knowledge/README.md:8–22`):

> ### Investigator-owned
>
> | File | Purpose |
> | --- | --- |
> | `investigator-field-template.md` | **OUTPUT CONTRACT** — exact shape of `run-state.json` |
> | `products.md` | Product name → directory mapping + override patterns + product rules |
> | `themes.md` | Theme roster — Platform dir, subfolder, levels, aliases, doNotTouch |
> | `attachment-analysis.md` | Investigator's guide for extracting info from screenshots |
>
> ### Developer-owned
>
> | File | Purpose |
> | --- | --- |
> | `developer-field-template.md` | **OUTPUT CONTRACT** — `development` slice schema + branch rule |

`principles.md` is shared by both — it's universal reasoning, not owned by either agent.

## Conventions — why these files are grep-friendly

`knowledge/README.md:23–32`:

> 1. **5-line TL;DR at top** of every file — what to grep for, what you'll find.
> 2. **Alphabetized sections** (products, themes) or enum-ordered (fix categories).
> 3. **`## <key>` heading pattern** so grep `## Westlaw Advantage` works directly.
> 4. **Tables, bullets, YAML blocks — no prose paragraphs.** Reference material, not essays.
> 5. **Cross-references as relative links** — `themes.md#indigo`.
> 6. **`## Placeholder` marker** where data is missing. Grep `## Placeholder` to find gaps.
> 7. **Each file stays under ~250 lines** — split into sub-files under `references/` if a section grows.

These conventions are not stylistic preferences. Each one supports a specific agent runtime behaviour:

- **Convention 3 (`## <key>` heading pattern)** is what makes investigator Phase 5 work. The investigator runs `Grep "## <product-name>"` against `products.md` to find the product's section. If product names weren't in `## ` headings, this wouldn't grep cleanly.
- **Convention 4 (no prose)** is what keeps the file short and answers single-shot. An agent grepping for `themeDir: ` wants to find the path on the next line, not a five-paragraph essay about theme history.
- **Convention 6 (`## Placeholder`)** is how the plugin tracks known gaps. When porting to a new repo, `Grep "## Placeholder"` lists every missing entry that needs to be filled in. The investigator sets `productDir: null` and gates to the user when it hits a placeholder section, never guesses.
- **Convention 7 (250-line cap)** keeps the file in one Read call. The investigator can read `products.md` whole; if products grew beyond ~250 lines, the file would be split.

## Genre 1: Output contracts (field templates)

The most important convention in the plugin. Each agent's output schema lives as a markdown file the agent reads at runtime — not as text embedded in the agent's system prompt.

`investigator-field-template.md:1–7`:

> # Investigator Field Template (runtime-authoritative)
>
> **Purpose:** This file is the **exact output contract** for the `a11y-investigator`
> agent. At runtime the agent MUST Read this file in Phase 0 and produce
> `run-state.json` that matches this skeleton. Every project can edit this template to
> change what the investigator writes — without touching the agent.

The hard rules at the top of the template (`investigator-field-template.md:10–27`):

> 1. Write **only** fields listed in the skeleton below.
> 2. Do **NOT** add fields. If you have information outside the skeleton, put it in `additionalNotes[]`.
> 3. Every required field must be present. Use `null` or `""` or `[]` for empty, never omit.
> 4. If you cannot populate a required field even with best-effort inference, set `decision.status = "needs-user-clarification"` with the appropriate `gateReason`.
> 5. Fields in `### FORBIDDEN FIELDS` at the bottom are **never** to appear in the output, even if the raw ADO payload contains them. Dropping them is part of your job.
> 6. **No populated knowledge entry → null value → gate on critical fields.** [...] Do NOT guess a plausible-looking path or directory.

Read these as architectural rules, not guidelines:

- Rule 2 means the agent's output shape is **constrained by the file**, not by the LLM's improvisation.
- Rule 3 means downstream consumers can rely on field *presence* — they never have to write `if x in obj`.
- Rule 4 means "I don't know" is a structured output (`needs-user-clarification` + `gateReason`), not a hallucinated value.
- Rule 5 means input filtering is an explicit responsibility — see "FORBIDDEN FIELDS" below.
- Rule 6 means "I can't find it in the knowledge base" is *also* a structured output (null → gate), not a guessed path.

### The schema as YAML skeleton

The body of the field template is a YAML skeleton with placeholders (`investigator-field-template.md:30–181` — excerpt):

```yaml
classification:
    product:
        name: '<canonical product name from knowledge/products.md>'
        productDir: '<VERBATIM directory from products.md entry; null if no populated entry exists. NEVER guess a plausible path.>'
        overrideFile: "<map.config.js path, or ''>"
        confidence: "<'High' | 'Medium' | 'Low'>"
        reasoning: '<cite signal sources: tag, field, attachment, knowledge file>'

    theme:
        name: '<theme name from knowledge/themes.md>'
        themeDir: '<VERBATIM directory from themes.md entry; null if themes.md has no populated entry. NEVER guess a plausible path.>'
        inferred: <true | false>
        confidence: "<'High' | 'Medium' | 'Low' — MUST downgrade when inferred=true>"
```

The placeholder text is *itself* part of the contract. "VERBATIM directory from products.md entry; null if no populated entry exists. NEVER guess a plausible path." is a runtime instruction baked into the schema. The agent reads the placeholder, understands the rule, and follows it.

### Why the schema is a file, not a system-prompt block

Three reasons the field template lives outside the agent:

1. **Edit without touching the agent.** Adding a field to the schema means editing `investigator-field-template.md`. No agent file changes. No re-deploy. Bump `runMeta.schemaVersion` so consumers know what to expect.
2. **Cheap context.** The agent reads ~5 KB of schema once per run; the agent file itself stays focused on *flow* (the 9-phase discovery), not output shape.
3. **Per-project customization.** Different TR repos may want different fields. Forking the plugin and editing the field template adapts the output without changing the agent's system prompt.

Doc 09 lists this as pattern 5 (Output contract as edited file).

### `FORBIDDEN FIELDS` — the deny-list

The investigator reads raw ADO work-item JSON. ADO returns a *huge* payload with fields like `System.BoardColumn`, `WEF_BC1234`, `Microsoft.VSTS.Common.StackRank` — bookkeeping fields that have nothing to do with the bug. The agent must drop them.

`investigator-field-template.md:185–246` is the deny-list:

> ## FORBIDDEN FIELDS — never write these
>
> The raw ADO payload contains many fields that are bookkeeping-only. The agent MUST drop them. Do not write any field in this list, even if the raw response has it.
>
> ### Top-level
> - `state` at top level (duplicates `runMeta.phase`)
>
> ### `bug.*`
> - `bug.id` (duplicates top-level `bugId`)
> - `bug.type` (always "Bug")
> - `bug.assignedTo`
> - `bug.createdBy`
> - `bug.createdDate`
> - `bug.changedDate`
> - `bug.iterationPath`
> - `bug.systemInfo`
> [...]
>
> ### Kanban / ADO bookkeeping (any field matching these patterns)
> - `System.BoardColumn*`, `System.Board*`
> - `WEF_*`
> - `Microsoft.VSTS.Common.State*` (duplicates `bug.state`)
> [...]

Two design choices:

1. **Listing the forbidden fields explicitly** is what makes the agent's job tractable. Without this list, the agent would have to *infer* which fields matter — slow, error-prone, and inconsistent across runs.
2. **Pattern matches are allowed** (`WEF_*`, `Microsoft.VSTS.Common.State*`). The agent doesn't need to enumerate every Kanban-related field; it just drops anything matching the pattern.

This pattern generalises any time you forward an external payload (ADO, Jira, Salesforce) and want only a curated subset.

### `additionalNotes[]` — the escape valve

Schema rules are tight, which means the agent will sometimes have an observation that doesn't fit. The escape valve (`investigator-field-template.md:174–181`):

```yaml
additionalNotes: []
# Escape valve. If the investigator has an observation NOT captured by any field above,
# add it here as a short string. Example:
#   - "Bug attachment is corrupt — analysis skipped"
#   - "ADO custom field X.Y.Z was populated; not yet in template — consider adding"
# NEVER use this to smuggle in fabricated acceptance criteria, guessed component names,
# or any structured data that belongs in one of the fields above.
```

Two qualities of this escape valve:

1. **It's an array of strings**, not nested structured data. The agent can't smuggle in a fake `acceptanceCriteria` field by stuffing structured data into `additionalNotes`. It's free-form text only.
2. **The contract names what NOT to put here**. "NEVER use this to smuggle in fabricated acceptance criteria, guessed component names, or any structured data that belongs in one of the fields above." If you're tempted to put structured data in here, you should be adding a field to the schema instead.

This is one of the more delicate parts of the design. The escape valve is necessary (rare observations *do* happen), but it can become a hiding place for the LLM's hallucinations if you're not careful. Naming the prohibition is what keeps it useful.

## Genre 2: Universal reasoning rules — `principles.md`

Quoted from `principles.md:1–10`:

> # Universal A11y Principles
>
> Framework-agnostic reasoning the fixer applies to every bug, before any
> framework-specific or design-system-specific guidance. Stable across
> project changes, design systems, and specifications.
>
> The fixer should read this file once per run and keep it in context while
> iterating over bugs. It is NOT a recipe book — it's a set of reasoning
> rules that constrain which fix is correct.

The body has 9 sections (`§0` through `§9`), referenced throughout the developer agent's prompt as `principles §5 reasoning ladder`, `principles §6 anti-patterns`, `principles §9 self-verification checklist`, etc.

The opening section (`principles.md:14–30`) sets the mental model:

> ## 0. Mental model — work in the accessibility tree, not the DOM
>
> Assistive technologies (screen readers, voice control, switch devices)
> do not see your DOM. They see the **accessibility tree** — a projection
> computed by the browser from HTML semantics, ARIA attributes, and
> computed styles (`display`, `visibility`, `aria-hidden`).
>
> Before any fix, mentally reconstruct what an AT user perceives:
>
> - What **role** does this element expose?
> - What is its **accessible name** (what is read aloud)?
> - What **states and properties** are announced?
> - What **keyboard interactions** does it respond to?
> - What **relationships** does it expose (owner, controls, describedby)?

`principles.md` is *reasoning rules*, not *project data*. It doesn't change when you fork the plugin to a new TR repo. It evolves slowly, when WCAG itself evolves or when the team learns a new anti-pattern.

The split between `principles.md` (genre 2) and `products.md` / `themes.md` (genre 3) is the reason the plugin is portable. Quoting `README.md:97–110`:

> The chassis (agents, commands, skills) is repo-agnostic. Codebase-specific data is isolated in `plugins/a11y/knowledge/`:
>
> | File | Codebase-specific? |
> | --- | --- |
> | `products.md` | Yes — product → directory mapping |
> | `themes.md` | Yes — theme detection rules |
> | `principles.md` | No — universal WCAG reasoning, reusable as-is |
> | `attachment-analysis.md` | No — screenshot-reading guide, reusable |
> | `*-field-template.md` | No — output schemas, reusable |
>
> To target another TR frontend repo: fork the plugin, edit `products.md` and `themes.md` to match the new repo's structure, and you're running. No agent / command changes required.

If you're authoring a similar plugin: separate genre-2 (universal reasoning) from genre-3 (project-specific) as cleanly as possible. Genre 2 stays stable; genre 3 is the porting interface.

## Genre 3: Project-specific data — `products.md` and `themes.md`

These two files hold the codebase-specific facts the agents need to do their job. They're the only files you edit when porting the plugin to a new repo.

The format follows the conventions: a 5-line TL;DR, then a series of `## <key>` sections with structured YAML / table content. The investigator greps for `## <product-name>` (`agents/a11y-investigator.md:187`) and reads the matched section to extract the directory path, override file location, and any product-specific rules.

A representative entry might look like (synthetic example — actual file may have different products):

```markdown
## Westlaw Edge

productDir: Products/Westlaw/Edge
overrideFile: ''
themes:
  - default
  - indigo
```

Why is this structured rather than prose? Because the agent extracts specific values:

- `Grep "## Westlaw Edge"` finds the section.
- `Read` the section.
- Parse `productDir:` to get `Products/Westlaw/Edge`.
- Parse `themes:` to validate the bug's theme is one this product has.

If the data were prose ("Westlaw Edge code lives at `Products/Westlaw/Edge`. The available themes are default and indigo."), the agent would have to do natural-language extraction, which is slower and less reliable.

The `themes.md` file follows the same pattern, with a different schema reflecting theme-specific data (CSS subfolder paths, levels, aliases, `doNotTouch` globs).

## Genre 4: Prompt guides — `attachment-analysis.md`

Genre-4 files are *instructions for an agent on how to do a sub-task*. They're not data the agent looks up; they're prompts the agent loads into context.

`attachment-analysis.md:1–7`:

> # Attachment Analysis Guide
>
> **TL;DR:** Instructions for the investigator on how to extract structured information
> from ADO bug screenshots. Populates `attachments[].analysis.*` in the work order.
> This is a **prompt guide**, not a data file — it tells the investigator what to look for
> and how to report it.

The investigator's Phase 4 (Attachments) does whole-file `Read` of `attachment-analysis.md` and follows its instructions when looking at downloaded screenshots. The file enumerates the fields to populate (`componentShown`, `affectedElements`, `visualIssue`, `colors`, `textVisible`, etc.) and gives extraction guidance for each (`attachment-analysis.md:22–60`).

Why split this into a separate file rather than embed in the agent prompt?

- **Methodology evolves.** As the team learns better ways to extract info from screenshots, they edit `attachment-analysis.md`. Agents pick up the new methodology on next run.
- **Cost.** The agent only loads this file when it's actually doing screenshot analysis (Phase 4). Other phases don't pay the token cost.
- **Reusability.** A future agent (a verifier? a screenshot-comparing reviewer?) can also load this file, sharing the methodology.

The pattern is: **load detailed sub-task instructions on demand, don't bake them into the agent's main prompt.**

## Field template enforcement — what happens at runtime

Tying genres 1 and the agents together — let's trace exactly what happens when the developer agent runs.

1. **Spawn**: slash command spawns the developer with `RUN_DIR` and any flags.
2. **Step 1a (mandatory)**: agent does parallel `Read`:
   ```
   Read ${CLAUDE_PLUGIN_ROOT}/knowledge/developer-field-template.md
   Read ${CLAUDE_PLUGIN_ROOT}/knowledge/principles.md
   ```
3. **Step 1b**: agent reads run-state, validates phase, extracts slices.
4. **Steps 2–6**: agent does the actual work (knowledge lookups, Saffron MCP, source reads, edits, lint, test).
5. **Step 7 — Final write**: agent writes `run-state.json`. Constructs the `development` slice, **comparing every field against `developer-field-template.md` Part 3**. Drops any field listed in Part 4 (FORBIDDEN FIELDS). Uses `additionalNotes[]` for observations not in the schema.

The field template is checked at write time, not at read time. The agent's output is constrained by the schema it loaded in Step 1a.

The developer's spec spells this out (`agents/a11y-developer.md:564`):

> **NEVER:** Write any field outside `developer-field-template.md` Part 3.

And:

> **NEVER:** Touch investigator-owned fields (`bug.*`, `attachments.*`, `classification.*`, `decision.*`, etc.) — see `developer-field-template.md` Part 4 FORBIDDEN FIELDS.

The agent uses the field template to:

- Construct its own output shape (Part 3).
- Avoid touching upstream slices (Part 4).
- Find the escape valve when needed (`additionalNotes[]`).

## Porting checklist

If you fork this plugin to a new TR frontend repo:

1. **Edit `products.md`.** Replace the existing product list with your repo's. Use the same `## <product-name>` heading + structured YAML format. Run `Grep "## Placeholder"` to verify nothing's missing.
2. **Edit `themes.md`.** Same pattern — list every theme that exists in your repo.
3. **Don't edit `principles.md`, the field templates, or `attachment-analysis.md`.** Those are repo-agnostic.
4. **Don't edit the agents or slash commands.** They reference the knowledge files via `${CLAUDE_PLUGIN_ROOT}` and pick up your edits automatically.
5. **Smoke-test.** Run `/a11y:investigate AB#<known-bug-id>` and verify the resulting `run-state.json` has `productDir` set correctly (not null, not a guessed path).

If something else needs to be different for your repo (e.g., the WCAG criteria the team prioritises differently, or the framework signals that the developer uses to pick `framework: react|angular`), check whether the difference belongs in genre 3 (extend `products.md` / `themes.md`) or genre 1 (modify the field template). Don't put it in genre 2 — that's universal — and don't put it in the agent prompt — that defeats the porting design.

## Checklist: designing a knowledge base

If you're authoring a `knowledge/` folder for your own plugin:

1. **Name the genres** explicitly. Don't have a single mixed `kb.md`. Decide upfront:
   - Output contracts (one per agent that produces output).
   - Universal reasoning (one or more).
   - Project-specific data (one per data dimension).
   - Prompt guides for sub-tasks (one per sub-task that benefits from explicit methodology).

2. **Each file has a 5-line TL;DR at the top.** What this file is, when to read it, what to grep for.

3. **Use `## <key>` headings.** Make grep work. No prose paragraphs as primary content.

4. **Field templates are runtime-authoritative.** The agent reads them on every run; they're the source of truth for output shape. Never embed schema in the agent prompt.

5. **Field templates have a `FORBIDDEN FIELDS` deny-list.** Especially if your agent forwards an external payload (API response, large JSON). Pattern-match where possible.

6. **Field templates have an `additionalNotes[]` escape valve.** Free-form strings only. Document what NOT to put there.

7. **Project-specific data is the porting interface.** Keep it minimal — one or two files. Universal stuff goes elsewhere.

8. **Cap each file at ~250 lines.** If a section grows, split it into `references/<section>.md`.

9. **Use `## Placeholder` markers** for known gaps in project-specific files. Greppable, fillable later.
