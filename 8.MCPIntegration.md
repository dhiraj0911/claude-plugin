# 08 — MCP integration: bundled and project-level servers

> A plugin can bundle MCP servers in its own `.mcp.json`. The plugin's `--init-script` lever lets you inject vendored assets (like axe-core) into every page a browser MCP visits. This is the most powerful integration mechanism in the plugin.

---

## What an MCP server is, in 60 seconds

The Model Context Protocol (MCP) is a wire protocol for "tool servers" — external processes that expose tools, resources, and prompts to LLMs. Claude Code spawns or connects to these servers and routes tool calls between the LLM and the server.

A server might:

- **Run as a subprocess** (`stdio`): Claude Code spawns `npx -y @some/mcp-server`, talks JSON-RPC over stdin/stdout.
- **Be reached over HTTP**: Claude Code makes HTTP requests to a remote URL.

You don't need to write your own MCP server to use this plugin's patterns. You just need to know that *configuring* an MCP server means writing a JSON entry under `mcpServers` in a `.mcp.json` file, and that entries can live at three levels:

| Level | Location | When to use |
| --- | --- | --- |
| **User** | `~/.claude.json` (the `mcpServers` section) | Servers with credentials private to you. |
| **Project** | `<project>/.mcp.json` | Servers shared across the team via the codebase repo. |
| **Plugin** | `<plugin-root>/.mcp.json` | Servers integral to the plugin — bundle when the plugin can't function without them. |

When Claude Code starts, it merges all three levels. Tool names get namespaced so two servers with overlapping tool names don't collide (more on that below).

## The four MCP servers in this plugin

| Server | Where it lives | Used by | Why this level |
| --- | --- | --- | --- |
| `Ask Saffron MCP Server` | bundled in plugin `.mcp.json` | developer agent | TR-internal design system MCP. Plugin-specific; users shouldn't need to set it up themselves. |
| `playwright` | bundled in plugin `.mcp.json` | `a11y-browser-verify` skill | Needs `--init-script` pointing at the plugin's vendored axe.min.js — only the plugin knows that path. |
| `azure-devops` | project / user `.mcp.json` | investigator | Needs the user's Azure CLI token. Bundling would mean baking the project alias (`TR-Legal-Cobalt`) into the plugin, which leaks codebase-specific config. |
| `github` | project / user `.mcp.json` | investigator + developer | Needs the user's `GITHUB_PAT`. Bundling makes credential management awkward. |

The split is meaningful. **Bundle servers that are tightly coupled to plugin assets or plugin-specific business logic. Leave servers that are tightly coupled to user credentials at the user / project level.**

## The bundled `.mcp.json`

Here is the entire bundled file — `plugins/a11y/.mcp.json:1–24`:

```json
{
  "mcpServers": {
    "Ask Saffron MCP Server": {
      "type": "http",
      "url": "https://aideployment-prod.plexus.gcs.int.thomsonreuters.com/207870/ask-saffron-mcp/",
      "headers": {
        "x-user-email": "Dhiraj.RajeshBari@thomsonreuters.com",
        "x-organization-name": "Thomson reuters",
        "x-user-id": "C304925",
        "x-workspace": "C:/Users/C304925/cobalt_static-content"
      }
    },
    "playwright": {
      "command": "npx",
      "args": [
        "-y",
        "@playwright/mcp@latest",
        "--browser", "chrome",
        "--ignore-https-errors",
        "--init-script", "${CLAUDE_PLUGIN_ROOT}/scripts/axe.min.js"
      ]
    }
  }
}
```

Two servers with very different shapes. Let's look at each.

### `Ask Saffron MCP Server` — HTTP MCP

This is a remote MCP service hosted by TR. The plugin's `.mcp.json` tells Claude Code:

- `type: "http"` — connect over HTTP, not as a subprocess.
- `url` — the endpoint.
- `headers` — identity headers sent on every request.

The `headers` block is where the *one* user-specific config lives in this bundled file: the `x-user-email`, `x-user-id`, and `x-workspace` are personal to whoever installed the plugin. The setup guide acknowledges this is awkward (`docs/setup-guide.md:103`):

> **Don't commit your real values.** The `.mcp.json` ships with placeholder/sample creds. Either set yours locally and avoid committing, or move Saffron to your user-level `.mcp.json`.

So this is a compromise: bundle the URL and the header *names* (which never change), but each user has to plug in their own values. Not ideal, but pragmatic. The alternative — making every user manually configure the entire Saffron entry — is much worse for adoption.

### `playwright` — stdio MCP with `--init-script`

This is the elegant one. `npx -y @playwright/mcp@latest` runs the published Playwright MCP server. The four flags do specific work:

| Flag | Effect |
| --- | --- |
| `--browser chrome` | Use the user's installed Chrome (not bundled Chromium). |
| `--ignore-https-errors` | Tolerate self-signed certs (useful for dev / staging / VPN-internal pages). |
| `--init-script <path>` | Inject this JS into **every page** the browser navigates to, before any page script runs. |

The `--init-script` value is `${CLAUDE_PLUGIN_ROOT}/scripts/axe.min.js`. Three things make this work:

1. **`${CLAUDE_PLUGIN_ROOT}` resolves to the plugin's cache directory at runtime.** No relative paths, no hardcoded absolute paths. The MCP server gets a real filesystem path it can read.
2. **The script (axe-core 4.11.4) is bundled with the plugin.** When you install the plugin, axe gets copied into the cache alongside `.mcp.json`. There's nothing to download at runtime, no CDN to depend on, no version to drift.
3. **`--init-script` is a Playwright primitive, not a Claude-specific thing.** Playwright supports running a script in every page context before page scripts. The plugin reuses this primitive for asset injection.

The skill (`a11y-browser-verify`) then assumes axe is "just there" on every page (`SKILL.md:160–163`):

```javascript
if (typeof window.axe?.run !== 'function') {
  return { error: 'axe-core not loaded — init-script may have failed' };
}
```

If the init-script worked, `window.axe.run` exists, the skill calls it, gets the violations, writes the report. No download step at scan time. Fast, offline-capable, version-pinned.

## Tool-name namespacing

When Claude Code merges MCP servers from all three levels (user / project / plugin), tool names are namespaced to avoid collisions:

| Server location | Tool name pattern |
| --- | --- |
| User or project `.mcp.json` server `foo` | `mcp__foo__<tool-name>` |
| Plugin `<plugin>` server `foo` | `mcp__plugin_<plugin>_<sanitized-server-name>__<tool-name>` |

Concrete examples from this plugin:

| Server | Origin | Sample tool |
| --- | --- | --- |
| `azure-devops` | project `.mcp.json` | `mcp__azure-devops__wit_get_work_item` |
| `github` | project `.mcp.json` | `mcp__github__search_pull_requests` |
| `Ask Saffron MCP Server` | plugin `.mcp.json` | `mcp__plugin_a11y_Ask_Saffron_MCP_Server__get-saffron-tokens` |
| `playwright` | plugin `.mcp.json` | `mcp__plugin_a11y_playwright__browser_navigate` |

The plugin prefix (`plugin_a11y_`) means two installations of "a Playwright MCP server" — one bundled in this plugin, one configured at user level — don't collide. Each gets its own namespaced tool family.

This matters when you write `allowed-tools` on an agent. The investigator's allowlist uses bare names because those servers come from the user / project level:

`agents/a11y-investigator.md:9–16`:

```yaml
allowed-tools:
    - Read
    - Grep
    - Glob
    - Write
    - Bash
    - mcp__azure-devops__*
    - mcp__github__*
```

The developer's allowlist names Saffron with the plugin prefix:

`agents/a11y-developer.md:18–21`:

```yaml
    - mcp__Ask_Saffron_MCP_Server__get-saffron-tokens
    - mcp__Ask_Saffron_MCP_Server__get-saffron-a11y-attributes
    - mcp__Ask_Saffron_MCP_Server__get-saffron-code-equivalent
    - mcp__Ask_Saffron_MCP_Server__get-saffron-code
```

Wait — those don't have the `plugin_a11y_` prefix. Why? Because Claude Code resolves namespacing at runtime: from inside an agent in the `a11y` plugin, the bundled `Ask Saffron MCP Server` *is* the local Saffron server, and the harness also makes it available under the unprefixed name. The full prefixed name (`mcp__plugin_a11y_Ask_Saffron_MCP_Server__*`) is what you'd use from outside the plugin, e.g., from the user's permissions allowlist (`docs/setup-guide.md:249`):

```json
"mcp__plugin_a11y_Ask_Saffron_MCP_Server__*",
"mcp__plugin_a11y_playwright__*",
```

The double form (prefixed for permissions, unprefixed for in-plugin allowed-tools) is ergonomic but worth remembering: *if the same MCP server is exposed at multiple levels, the namespace prefix tells you which level you mean.*

## When to bundle vs leave at user/project level

Three guiding questions:

### 1. Does the server depend on plugin assets?

If yes: bundle. The Playwright server in this plugin has `--init-script` pointing at a plugin-bundled file (`axe.min.js`). Only the plugin knows that path; only the plugin can keep the asset version in sync. Leaving Playwright at user level would mean every user manually configuring the init-script path, which is brittle and decouples the plugin from its own assets.

### 2. Does the server use user-specific credentials?

If yes: leave at user level (or project level if shared with the team). The Azure DevOps server uses `az login` tokens, which are personal. The GitHub MCP server uses `$GITHUB_PAT`, which is personal. Bundling either one would either bake the user's credentials into the plugin (insecure) or require every user to edit the bundled file (annoying and error-prone).

### 3. Is the server semi-private — credentials per-user but configuration shared?

This is the awkward case the Saffron server lives in. The URL and header *shape* are shared (TR-internal), but each user has their own `x-user-email` etc. The plugin bundles the file but ships placeholders and tells users "edit your identity headers locally; don't commit your real values." The setup guide (`docs/setup-guide.md:82–103`) walks through it.

A cleaner alternative would be moving Saffron to user-level entirely, with the plugin's docs describing the required entry. The plugin chose to bundle it because Saffron is plugin-specific (no other plugin uses it) and bundling reduces the manual setup steps for new users.

## The `--init-script` lever, generalised

The pattern is **bundle a JS asset in the plugin, point an MCP server's `--init-script` (or equivalent flag) at it, let the asset run in every page context.**

Use cases beyond axe-core:

| Asset to inject | Use case |
| --- | --- |
| `lighthouse.bundle.js` | Run Lighthouse audits inside MCP-driven browsers. |
| Custom DOM observers | Track CLS / LCP / unhandled errors during a scripted browser session. |
| Polyfills | Make a flag-gated newer JS API available on older pages for testing. |
| Telemetry shims | Capture all `fetch` / `XMLHttpRequest` calls during a session for replay. |

The plugin's pattern works for any of these:

1. Vendor the asset to `plugins/<plugin>/scripts/<asset>.min.js`.
2. Reference it via `${CLAUDE_PLUGIN_ROOT}/scripts/<asset>.min.js` in the bundled `.mcp.json`'s server args.
3. Add a refresh recipe and a license note to `plugins/<plugin>/scripts/README.md`.
4. Document the asset's API surface — what global it sets up, how skills should detect it.

Doc 09 lists this as pattern 11 (Vendored assets via `--init-script`).

## Permissions — taming MCP prompt fatigue

MCP tools, like all Claude Code tools, fire permission prompts on first use. With four MCP servers exposing dozens of tools, that's a lot of prompts. The setup guide gives a recommended allowlist (`docs/setup-guide.md:226–262`):

```json
{
  "permissions": {
    "allow": [
      "Bash(mkdir:*)",
      "Bash(az rest:*)",
      "Bash(gh pr list:*)",
      "Bash(gh pr view:*)",
      "Bash(gh pr create:*)",
      "Bash(gh pr checks:*)",
      "Bash(gh api:*)",
      "Bash(git status:*)",
      "Bash(git diff:*)",
      "Bash(git log:*)",
      "Bash(git rev-parse:*)",
      "Bash(git branch:*)",
      "Bash(git checkout:*)",
      "Bash(git add:*)",
      "Bash(git commit:*)",
      "Bash(npx:*)",
      "mcp__plugin_a11y_Ask_Saffron_MCP_Server__*",
      "mcp__plugin_a11y_playwright__*",
      "mcp__github__*",
      "mcp__azure-devops__*",
      "Read(./.a11y/**)",
      "Write(./.a11y/**)",
      "Edit(./.a11y/**)"
    ]
  }
}
```

Three design choices in this allowlist:

1. **MCP servers get blanket allows** (`mcp__plugin_a11y_playwright__*`). This is reasonable — the MCP server itself is trusted; the plugin author chose it. Per-tool prompting would be overkill.
2. **`gh` and `git` get specific subcommand allowlists** (`Bash(gh pr create:*)`, `Bash(git checkout:*)`). This is the security trade: `gh` and `git` can be called with arbitrary args, and you don't want one specific subcommand auto-approved (`git push`) while others stay prompted (`git push --force`). The plugin allows the *safe* subcommands and leaves the dangerous ones (git push, rm) to keep prompting.
3. **File operations are scoped to `./.a11y/**`** (`Read(./.a11y/**)`, `Write(./.a11y/**)`). The plugin writes to its own subtree freely; source-code edits still prompt. Means the agent can write `run-state.json` without prompting but can't silently overwrite `package.json`.

The pattern: **scope permissions by both *target* (which MCP server, which directory) and *operation* (which Bash subcommand, Read vs Write).** Doc 09 lists this as part of pattern 18 (Tool-name namespacing across plugins).

## Background mode and permissions

The investigator's `--bg` flag lets it run the agent in a background task. Background runs cannot prompt for permissions interactively — a permission prompt mid-run hangs the background process. So before using `--bg`, you must pre-approve a broader allowlist.

`docs/state.md:122–144`:

> When you run an agent with `--bg`, Claude Code can't interactively prompt you for tool approvals. A permission prompt mid-run will hang the background process. Before using `--bg`, pre-approve a broader allowlist than the interactive case — `--bg` needs unattended file edits, so blanket `Read` / `Write` / `Edit` is appropriate.

The `--bg` allowlist includes blanket `Read`, `Write`, and `Edit` (no path restriction), plus blanket `Bash(git:*)` and `Bash(gh:*)`. That's wider than the interactive list, intentionally — background mode trades safety for "leave the room and check back in 10 minutes."

If you author your own plugin with long-running agents, consider:

- Document the recommended interactive allowlist (tighter).
- Document the recommended `--bg` allowlist (wider).
- Make the difference explicit so users understand the tradeoff.

## Setup-guide responsibilities

When you bundle MCP servers, the burden on the user goes up. Make sure the plugin's setup guide covers:

1. **Prerequisites for spawning each server.** Playwright needs `npx`. Saffron needs network access to `aideployment-prod.plexus.gcs.int.thomsonreuters.com`. ADO MCP needs `az login`. GitHub MCP needs `$GITHUB_PAT`.
2. **Identity / credential setup.** Where to put `GITHUB_PAT`, how to authenticate `az login`, what header values to plug into the bundled `.mcp.json`.
3. **Verification step.** "After install, run `/mcp` inside Claude Code and verify all four servers appear." The footer count signal in `setup-guide.md:194–204` does this — `... 3 agents · 3 commands · 6 skills · 2 plugin MCP servers ...`
4. **Troubleshooting table.** What to do if `npx -y @playwright/mcp@latest` fails (corporate proxy?), what to do if `az rest` returns 401 (stale token), what to do if axe says "not loaded" (cached plugin out of date — `sync-plugin.sh` or `/reload-plugins`).

`docs/setup-guide.md:328–346` has the troubleshooting table for this plugin. Borrow the format.

## Checklist: integrating MCP servers in your plugin

If you're authoring a plugin that uses MCP servers:

1. **Decide the level for each server.**
   - Bundle if the server depends on plugin assets (`--init-script`, hardcoded URL the plugin provides).
   - Leave at user / project level if the server uses personal credentials.
2. **For bundled servers:**
   - Use `${CLAUDE_PLUGIN_ROOT}` for any path argument.
   - Document required user edits in the setup guide (e.g., identity headers).
   - Don't bundle real credentials — use placeholders.
3. **For user / project servers:**
   - List the JSON entry verbatim in the setup guide.
   - Document the credential / env var setup.
4. **Tool-name namespacing:**
   - Use `mcp__plugin_<plugin>_<server>__*` in the user's permissions allowlist.
   - Use the unprefixed name (`mcp__<server>__*`) in agents that live inside the same plugin.
5. **For each MCP server you call from agents:**
   - Add to the agent's `allowed-tools` (with appropriate prefix or wildcard).
   - Document expected failure modes in the agent's spec ("if Saffron returns nothing, fall back to grep").
6. **For vendored assets injected via `--init-script`:**
   - Vendor the asset to `scripts/<asset>.min.js`.
   - Reference it via `${CLAUDE_PLUGIN_ROOT}/scripts/<asset>.min.js`.
   - Document the asset's version, license, and refresh procedure in `scripts/README.md`.
   - Add a runtime detection check in any code that uses the asset (`typeof window.<global> === 'function'`).
7. **Setup guide:**
   - List prerequisites for each server.
   - Walk through credential / env var setup.
   - Provide a verification command (`/mcp`).
   - Include a troubleshooting table.
8. **Permissions:**
   - Provide both an interactive allowlist (tight) and a background allowlist (wider).
   - Scope by target (MCP server, directory) and operation (specific Bash subcommand).
