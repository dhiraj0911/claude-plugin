# 09 — Design patterns

> A field guide to the generalizable patterns in this plugin. Each entry: **name → problem → solution → anchor in this plugin → when to use elsewhere.** Skim, bookmark, copy.

---

## How to read this

Each pattern is independent. You can apply any one without the others; they compose well but don't depend on each other. Read in order if you're new; jump if you're hunting for something specific.

The patterns roughly cluster into:

- **Multi-agent orchestration** (1, 2, 3, 8, 14)
- **Agent design discipline** (4, 5, 7, 9, 10, 16)
- **State management** (6, 15)
- **External tool integration** (11, 12, 17)
- **UX inside agents** (13, 18)

## 1. Phase lock for multi-agent state machines

**Problem.** You have multiple autonomous agents that should run in a strict order. They might be invoked in the wrong order (user mistake), invoked twice (rerun), or interrupted mid-run (crash). How do you keep the workflow consistent without inventing a process supervisor?

**Solution.** Add a single `phase` field to your shared state. Define a finite enum of legal values + transitions. Every agent reads the field on entry, refuses if it's not the expected value, and updates it on exit. Terminal states (`done`, `failed`, `refused`, `aborted`) are dead-ends.

**Anchor.** `docs/state.md:21–31` defines the enum:
```
investigating → ready-for-developer → implementing → ready-for-verify → shipping → done
                                                                                ↘ failed
                                                                                ↘ refused
                                                                                ↘ aborted
```
The shipper's preflight (`agents/a11y-shipper.md:42`) checks `runMeta.phase == 'ready-for-verify'`. The investigator's exit (`agents/a11y-investigator.md:285–288`) sets the next phase.

**Reuse.** Any time you have ≥2 agents collaborating sequentially. The phase field doubles as a debugging aid — `cat run-state.json | jq .runMeta.phase` tells you exactly where in the pipeline you are.

## 2. Atomic single-write at agent end

**Problem.** Agents that update a shared state file mid-run leave it in inconsistent shapes if they crash. Multi-step writes (`Edit` for slice A, then `Edit` for slice B, then `Edit` for `runMeta`) are slow, fragile, and unauditable.

**Solution.** The agent accumulates everything in working memory through its run. At the end — Step 7, Step 4, whatever the last step is — it does ONE `Write` of the complete file. No mid-run checkpoints. If it crashes, the file is the prior agent's last-known-good state.

**Anchor.** `agents/a11y-developer.md:564–565`:
> **NEVER** Use `Edit` on `run-state.json`. Step 7 is ONE atomic `Write` of the full file. Multiple incremental Edits are forbidden — they're slow, fragile, and produce unauditable partial state.

**Reuse.** Any state file that's read + written by multiple processes. The pattern needs a "construct-in-memory, write-once" discipline in your agent prompts. It pairs naturally with pattern 1 (phase lock) — atomic write on the terminal state transition.

## 3. Pure-worker subagents + orchestrator slash command

**Problem.** Autonomous agents that try to gate users mid-run have a structural issue: subagents in Claude Code can't call `AskUserQuestion`. So how does a multi-step workflow ask "Approve / Adjust / Discard" in the middle?

**Solution.** Split the workflow. The slash command runs in your main session — it can call `AskUserQuestion`, `AskUserQuestion`, do `git`, etc. The subagent is a pure worker — it does one self-contained task and returns. The slash command spawns the agent, waits for it, then runs the gate itself.

**Anchor.** `commands/developer.md:344–346`:
> - **Why orchestrator owns the gate:** `AskUserQuestion` is unavailable inside subagents. Putting the gate in this slash command (which runs in the main session) is the only architecturally sound way to make the user gate actually fire.

The agent's contract: `agents/a11y-developer.md:545`:
> **NEVER:** Call `AskUserQuestion`. The slash command owns user gating.

**Reuse.** Anywhere you need a user gate inside what looks like one workflow. If the user gate has to fire in the middle, the workflow is two phases: a worker phase and a gate phase. Put the worker in a subagent; put the gate in the slash command.

## 4. Mandatory-first-action preflight reads

**Problem.** Your agent's output schema or reasoning rules live in markdown files. The agent should consult them on every run, but LLMs sometimes "remember" prior runs (training contamination, in-session memory) and don't actually read.

**Solution.** Make the first tool call mandatory. The agent's `initialPrompt` or first body section says "Your FIRST tool call MUST be Read `<path>`." If the read fails (file missing, plugin cache broken), the agent refuses cleanly.

**Anchor.** Investigator's `initialPrompt` (`agents/a11y-investigator.md:21–22`):
> Phase 0: Your FIRST tool call MUST be Read `${CLAUDE_PLUGIN_ROOT}/knowledge/investigator-field-template.md`

Developer's first action (`agents/a11y-developer.md:79–86`):
> Your very first action MUST be a parallel batch of TWO Reads in one message: `developer-field-template.md` AND `principles.md`. If either Read fails, stop immediately, `Write` a minimal state with `development.status = "failed"`, return.

**Reuse.** Any time you have a runtime-loaded contract (output schema, reasoning rules, project-specific facts). The mandatory first read makes the contract part of the runtime, not part of the prompt — so editing the file changes behavior on next run, not on next plugin update.

## 5. Output contract as edited file (not prompt-embedded)

**Problem.** You want the agent's output schema to be project-customizable without re-deploying the agent. If the schema lives in the agent's system prompt, every change requires touching the agent.

**Solution.** Put the schema in a markdown file (`knowledge/<agent>-field-template.md`). The agent reads it via the mandatory-first-action pattern. Editing the schema means editing the markdown; no agent edit needed.

**Anchor.** `knowledge/investigator-field-template.md:1–6`:
> # Investigator Field Template (runtime-authoritative)
>
> **Purpose:** This file is the **exact output contract** for the `a11y-investigator` agent. At runtime the agent MUST Read this file in Phase 0 and produce `run-state.json` that matches this skeleton. Every project can edit this template to change what the investigator writes — without touching the agent.

The agent's enforcement (`agents/a11y-investigator.md:39–42`):
> **Output contract (runtime authoritative):** `knowledge/investigator-field-template.md` is the EXACT structure of `run-state.json`. You Read it in Phase 0 and write only fields listed there.

**Reuse.** Any agent with a structured output. Schemas in markdown, schemas with `# FORBIDDEN FIELDS` sections, schemas with `additionalNotes[]` escape valves — all editable, all sharable across team forks.

## 6. Project-data vs universal-reasoning split

**Problem.** Knowledge files mix two genres: facts that vary per project ("Westlaw lives at `Products/Westlaw/`") and reasoning that doesn't ("ARIA precedence: aria-labelledby > aria-label > native label"). Mixing them makes the plugin un-portable.

**Solution.** Two separate file genres. **Project data** (genre 3 in doc 07) goes in files like `products.md`, `themes.md` — edited when porting. **Universal reasoning** (genre 2) goes in `principles.md` — never touched per project. The agent loads both, but the porting process touches only genre 3.

**Anchor.** `README.md:97–110`:
> | File | Codebase-specific? |
> | --- | --- |
> | `products.md` | Yes — product → directory mapping |
> | `themes.md` | Yes — theme detection rules |
> | `principles.md` | No — universal WCAG reasoning, reusable as-is |

**Reuse.** Any plugin you'd like to use across multiple projects. Decide upfront which facts are project-specific and which are universal; put them in different files. Don't mix.

## 7. `FORBIDDEN FIELDS` deny-list

**Problem.** Your agent forwards an external payload (ADO API response, Jira issue JSON, Salesforce record). The payload has tons of fields you don't want. How do you tell the agent to drop them, in a way that scales as the source schema evolves?

**Solution.** A deny-list at the bottom of the field template. Pattern matches allowed (e.g., `WEF_*`, `Microsoft.VSTS.Common.State*`). The agent drops anything matching, even if the payload has new fields you haven't seen.

**Anchor.** `knowledge/investigator-field-template.md:185–246`:
> ## FORBIDDEN FIELDS — never write these
>
> The raw ADO payload contains many fields that are bookkeeping-only. The agent MUST drop them.
>
> ### Kanban / ADO bookkeeping (any field matching these patterns)
> - `System.BoardColumn*`, `System.Board*`
> - `WEF_*`
> - `Microsoft.VSTS.Common.State*`

**Reuse.** Any agent that consumes a verbose external payload and writes a curated subset. Put the deny-list near the schema definition; agents check both before writing each field.

## 8. Structured refusal categories

**Problem.** Agents fail in many ways: precondition not met, dependency missing, scope unclear, design-team-clarification-needed, etc. If the agent emits free-text reasons, the orchestrator can't branch on the cause. If it emits a single error code, you lose the diagnostic.

**Solution.** Two fields. `refusal.category` is a finite enum the orchestrator can branch on. `refusal.reason` is free-form text describing the specific instance. The enum has 4–5 values max, each with a clear meaning.

**Anchor.** `agents/a11y-developer.md:512–525`:
> | Trigger | Category | Reason template |
> | --- | --- | --- |
> | Phase precondition fails | `needs-manual` | "Entry phase=`<actual>`, expected `ready-for-developer`." |
> | Saffron `improvise` for color | `needs-external` | "Design team confirmation required for unresolved color(s)." |
> | Discovery budget exhausted | `needs-manual` | "Could not converge on fix target within 15-call budget." |
> | Knowledge file flags cross-repo | `needs-cross` | "Bug origin in `<other-repo>` per `<knowledge-file>`." |
> | Architectural change needed | `needs-refactor` | "Fix requires `<short>` — out of scope for attribute-level." |

The investigator's gate-reason enum is similar (`agents/a11y-investigator.md:268–275`):
> If `needs-user-clarification`, set `decision.gateReason` to exactly one of:
> - `cannot-resolve-product`
> - `theme-ambiguous`
> - `attachment-contradicts-ado`
> - `wcag-not-specified`
>
> Any other `gateReason` value is a bug.

**Reuse.** Anywhere an agent might fail in different ways. The enum drives orchestrator response; the free text helps the user / log reader understand the specific case.

## 9. Error budget on discovery

**Problem.** LLMs in open-ended search loops will keep grepping until they hit context limits. "One more grep" is a known failure mode that produces nothing useful and costs a lot.

**Solution.** Set a hard ceiling. The agent counts tool calls in working memory. When the count hits the cap, the agent refuses cleanly with a structured reason instead of trying harder.

**Anchor.** `agents/a11y-developer.md:251–264`:
> ### 3b. Fallback grep flow (BUDGETED — used when `targetFiles[]` empty or contradicted)
>
> Hard cap: **15 tool calls** total (Greps + Reads). Drill down once you have ≥2 hits in the same area.
>
> If budget hits 15 without convergence: `Write` at Step 7 with `development.status = "refused"`, `refusal = { category: "needs-manual", reason: "could not converge on fix target within 15-call budget" }`. Do NOT proceed to Step 4 with a guess.

The agent also dedupes (`agents/a11y-developer.md:565`):
> Re-issue an identical Grep or Read. Check `sourceDiscovery.queriesRun[]` / `filesRead[]` first.

**Reuse.** Any agent that does iterative discovery. Pick a number that's tight enough to force focus but loose enough to allow real exploration. Pair with dedup-before-dispatch.

## 10. Idempotency on every mutating action

**Problem.** Re-running an agent (because the user retried, because of a timeout, because of a flaky tool) shouldn't create duplicate work. PRs should not be created twice. Edits should not be layered.

**Solution.** Every mutating action checks state first. The shipper checks if a PR already exists for the branch (`gh pr list --head ...`). If yes, mark `already-shipped` and return without touching git. The developer checks if the change is already partially in source before editing.

**Anchor.** Shipper's PR-already-exists check (`agents/a11y-shipper.md:59–65`):
> **Idempotency.** Check if a PR already exists for this branch:
> ```bash
> gh pr list --head "<branch>" --state open --json number,url,title
> ```
> If a PR exists: write `shipping = { status: 'already-shipped', pullRequest: { number, url, isDraft: <bool> } }`, set `runMeta.phase = 'done'`, return without touching git.

Developer's idempotency rule (`agents/a11y-developer.md:389`):
> **Idempotency** — BEFORE editing, search for the change you're about to make. If already partially present, do NOT layer — record in `adaptations[]` and skip.

**Reuse.** Any agent that creates external artifacts (PRs, issues, files, commits) or modifies code. Check first; act second; record in state which path you took.

## 11. Vendored assets via `--init-script`

**Problem.** Your skill needs a JS library injected into every page (axe-core, Lighthouse, custom telemetry). CDN downloads at runtime are slow, fragile, and sometimes blocked by corporate networks.

**Solution.** Vendor the library in `plugins/<plugin>/scripts/<asset>.min.js`. Reference it as `${CLAUDE_PLUGIN_ROOT}/scripts/<asset>.min.js` in the bundled `.mcp.json`'s server args. The MCP server (Playwright in this plugin's case) accepts a `--init-script` flag that runs the vendored asset on every page before page scripts run.

**Anchor.** `.mcp.json:14–22`:
```json
"playwright": {
    "command": "npx",
    "args": [
        "-y", "@playwright/mcp@latest",
        "--browser", "chrome",
        "--ignore-https-errors",
        "--init-script", "${CLAUDE_PLUGIN_ROOT}/scripts/axe.min.js"
    ]
}
```

`scripts/README.md:7–14` explains the rationale:
> ## Why vendored, not from a CDN
>
> - Works offline / in air-gapped environments
> - No dependency on external CDN availability or TR network policy on cdnjs/jsdelivr
> - Reproducible: a given plugin version pins a specific axe rule set
> - Travels with the plugin via `${CLAUDE_PLUGIN_ROOT}` — referenced by absolute path in `.mcp.json`, no relative-path or sibling-folder fragility

**Reuse.** Any browser-driving skill that needs the same library on every page. Pin the version, add a refresh recipe, document the global the asset sets up.

## 12. `${CLAUDE_PLUGIN_ROOT}` for asset paths

**Problem.** Plugins live at two paths at runtime: source (where you authored it) and cache (where Claude Code copies it on install). Hardcoded paths break; relative paths break.

**Solution.** Use `${CLAUDE_PLUGIN_ROOT}` everywhere a plugin references its own assets. The harness expands it to the cache path at runtime.

**Anchor.** Used in:
- Agent reads (`agents/a11y-investigator.md:111`).
- Skill body reads (`skills/a11y-browser-verify/SKILL.md:274`).
- MCP server args (`.mcp.json:20`).

**Reuse.** Universal. If your plugin file references another plugin file, use `${CLAUDE_PLUGIN_ROOT}`.

## 13. Two-mode skill UX (one-shot vs interactive)

**Problem.** A user-invokable skill that drives an external resource (a browser, a database connection) sometimes needs the user to do setup before it can run — log in to a portal, navigate to a non-public page, etc. Forcing the URL as a required argument breaks the second case.

**Solution.** Make the URL argument optional. If passed, the skill auto-navigates. If omitted, the skill opens the resource (browser) and pauses, telling the user "do your setup; continue when ready."

**Anchor.** `skills/a11y-browser-verify/SKILL.md:14–16`:
```
/a11y-browser-verify https://example.com    # public URL — pre-navigates Chrome
/a11y-browser-verify                        # interactive — you log in / navigate before scanning
```

The Stage 1 ATTACH `AskUserQuestion` (`SKILL.md:55–60`) gives the user three options including "Use Chrome that's already open — paste the URL" — preserving any authenticated session the user already has open.

**Reuse.** Any skill that interacts with an external resource where authentication or navigation might be required. The two-mode UX makes the skill useful in both throwaway and authenticated contexts.

## 14. Forensic patch on Discard

**Problem.** When the user rejects an agent's work, you want to delete the branch and reset the tree. But: what if they change their mind tomorrow? Throwing away the diff means losing the LLM's reasoning.

**Solution.** Always save the diff to a `.patch` file *before* you `git branch -D`. The user can `git apply` later if they reconsider. Record the patch path in `revert.patchPath` so it's discoverable.

**Anchor.** `commands/developer.md:285–298`:
```bash
TS=$(date -u +%Y%m%dT%H%M%SZ)
git diff main..HEAD > <RUN_DIR>/rejected-diff-${TS}.patch
```
Then:
```bash
git checkout main
git branch -D <branch>
git status --short  # MUST be clean
```

And in run-state:
```
development.revert = { files: [...], patchPath: "<RUN_DIR>/rejected-diff-<TS>.patch" }
```

**Reuse.** Any rejection / abort path that destroys work. Save the work first; destroy second; record where the saved work lives.

## 15. `additionalNotes[]` escape valve

**Problem.** Your output schema is tight (good), but the agent occasionally observes something genuinely outside the schema. If you reject all out-of-schema observations, you lose useful information. If you allow them as structured fields, the schema becomes infinitely extensible and unreliable.

**Solution.** A flat array of free-form strings. Document what NOT to put there (no fabricated fields, no smuggled structured data). Useful for "skipped attachment because corrupt," "ADO returned an unexpected custom field," etc.

**Anchor.** `knowledge/investigator-field-template.md:174–181`:
```yaml
additionalNotes: []
# Escape valve. If the investigator has an observation NOT captured by any field above,
# add it here as a short string.
# NEVER use this to smuggle in fabricated acceptance criteria, guessed component names,
# or any structured data that belongs in one of the fields above.
```

**Reuse.** Any structured-output schema. Pair with explicit prohibition language ("don't put structured data here") so it doesn't become a hiding place.

## 16. Confidence rubric without fudge

**Problem.** LLMs are biased toward confident answers. Asked to score "High / Medium / Low," they tend to round up. The result: fabricated confidence in incorrect answers.

**Solution.** Score each *dimension* separately. Combine via explicit rules. Make "Low" a structured outcome that gates to the user, not a softer version of "Medium." Explicitly forbid the LLM from picking a value when the dimension is Low confidence.

**Anchor.** `agents/a11y-investigator.md:240–252`:
> Score each dimension (product, theme, WCAG SC specificity, attachment-ADO agreement) as Strong / Weak / None, then combine:
>
> - **High:** all Strong; no conflicts.
> - **Medium:** one dimension Weak but resolves; OR theme inferred; OR some signals absent without conflict.
> - **Low:** two+ dimensions Weak; OR attachment-ADO conflict; OR product genuinely ambiguous; OR WCAG SC missing.
>
> **Never guess.** If a dimension is Low confidence, gate to the user. Do NOT pick a value and report Medium. This is a hard rule — it is the single biggest v1 failure mode we are eliminating.

**Reuse.** Any agent that produces a confidence score. Decompose to dimensions, combine via rules, route Low to user gating.

## 17. Bundled-vs-user-level MCP split

**Problem.** Some MCP servers depend on plugin assets (`--init-script` paths, hardcoded URLs). Others depend on user credentials (`GITHUB_PAT`, `az login` tokens). Putting everything at one level fails one of the two cases.

**Solution.** Bundle servers tightly coupled to plugin assets in the plugin's `.mcp.json`. Leave servers tightly coupled to user credentials at the user / project level. Document both in the setup guide.

**Anchor.** `.mcp.json` bundles Playwright (needs init-script path) and Saffron (TR-internal URL). The setup guide expects `azure-devops` and `github` at the user / project level (`docs/setup-guide.md:111–129`).

**Reuse.** Any plugin that uses ≥2 MCP servers. Categorize each by "depends on plugin assets" vs "depends on user credentials" and route accordingly.

## 18. Tool-name namespacing across plugins

**Problem.** Two plugins can each include a Playwright MCP server. Their tool names would collide if there were no namespacing.

**Solution.** Plugin-bundled MCP tools get namespaced as `mcp__plugin_<plugin-name>_<server-name>__<tool-name>`. User / project servers stay un-prefixed (`mcp__<server-name>__<tool-name>`). Use the prefixed form in user permissions allowlists; use the un-prefixed form (or appropriate variant) in agent `allowed-tools` blocks within the plugin.

**Anchor.** Setup guide's permissions block (`docs/setup-guide.md:249–252`):
```json
"mcp__plugin_a11y_Ask_Saffron_MCP_Server__*",
"mcp__plugin_a11y_playwright__*",
"mcp__github__*",
"mcp__azure-devops__*",
```

**Reuse.** Universal. Any plugin that bundles MCP servers should use the prefixed form when documenting permissions, even if the unprefixed form also works in some contexts. The prefix makes the source unambiguous.

## When patterns conflict

Most of these patterns compose without friction, but a few have tradeoffs worth noting:

- **Pattern 4 (mandatory-first-action reads)** vs **Pattern 9 (error budget on discovery)**. The mandatory reads cost tool calls. If your budget is tight (15 calls), a pre-flight Read of two knowledge files eats 2/15. Make sure those reads add value relative to the budget.
- **Pattern 5 (output contract as edited file)** vs **Pattern 4**. The contract has to live in a file *and* be read on every run. If the file is large, it's expensive context. Cap files at ~250 lines per the knowledge-base conventions; split into sub-files (`references/`) when needed.
- **Pattern 10 (idempotency)** vs **Pattern 14 (forensic patch)**. Both require checking state before mutation. Combine them: the shipper's idempotency check happens before its push (no work to forensic-save); the developer's discard happens after edits (work-to-save exists). They run at different points; don't confuse.

## What's NOT a pattern

A few things in this plugin are domain-specific (TR-Saffron, Cobalt-static-content directories, WCAG criteria) and should not be lifted as patterns:

- **The 9-phase investigator flow.** This is bug-fix-specific. Your domain has its own discovery shape.
- **The 15-call budget number.** This is empirical; pick a number that fits your domain.
- **Saffron MCP resolution chain (mcp → grep → improvise).** This is design-system-specific. The general pattern is "primary source → fallback search → escape valve" — but the chain is bespoke.
- **The diff-review gate's three options (Approve / Adjust / Discard).** Your gate may have different options. The general pattern is "user gate inside a worker pipeline" (#3); the specific options are domain choices.

When porting a pattern, read the abstraction line ("phase lock for multi-agent state machines") and ignore the specific anchors.
