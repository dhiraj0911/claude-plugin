# 06 — Skills: user-invokable, reasoning helpers, and external MCP integration

> Two skill roles in this plugin. One drives a real browser through Playwright, injects a vendored library, and writes an interactive HTML report. The others are pure reference catalogs the developer agent loads when reviewing code.

---

## What a skill is

A skill is a directory at `skills/<name>/` containing at minimum a `SKILL.md` file. The frontmatter is metadata; the body is instructions.

Two roles in this plugin:

| Role | Example | How it's invoked |
| --- | --- | --- |
| **User-invokable** | `a11y-browser-verify` | User types `/a11y:a11y-browser-verify <url>`. Same surface as a slash command. |
| **Reasoning helper** | `expert`, `lint`, `localize`, `test`, `ux` | Loaded contextually by the developer agent when relevant rules apply. Not normally invoked by the user. |

The skill format is the same in both cases. The difference is in the `description` text — user-invokable skills are written to be discoverable as slash commands; reasoning helpers are written to be selected by their `description` keywords when an agent reasons "I'm reviewing CSS, I should load the `ux` skill."

A skill directory can also contain:

- `references/` — long-form reference docs the skill body points at ("read `references/jest.md` if you're using Jest").
- `rules/` — sub-files for rule categories ("apply the rules in `rules/colors.md`").
- `scripts/` — executable helpers (`*.mjs`) the skill spawns via Bash.

---

## User-invokable: `a11y-browser-verify` deep-dive

This skill is the most architecturally interesting artifact in the plugin. It drives a headed Chrome browser via the Playwright MCP server, injects axe-core to do an actual WCAG 2.1 AA scan, and writes a self-contained interactive HTML report. Read it carefully — it's a worked example of how a skill can orchestrate an external MCP server.

### Frontmatter

`skills/a11y-browser-verify/SKILL.md:1–5`:

```yaml
---
name: a11y-browser-verify
description: Run a live WCAG 2.1 AA accessibility audit on a web page using Playwright MCP + axe-core. Use when the user asks to "audit a page for accessibility", "run axe on this URL", "browser-verify a11y", "scan a page for WCAG violations", or wants an interactive accessibility report from a real headed browser.
argument-hint: "[<url>]"
---
```

The `description` is unusually long and keyword-rich. That's deliberate — this skill is user-invokable, and the `description` is what Claude matches when the user phrases their request in natural language. "Audit a page for accessibility," "scan a page for WCAG violations," and so on are all listed.

### The five-stage pipeline

The skill body (`skills/a11y-browser-verify/SKILL.md:27–33`):

```
PRE-CHECKS → ATTACH → READY → SCAN → PREVIEW → REPORT → DONE
                ↓        ↓              ↓         (conditional)
             [GATE]   [GATE]         [GATE]
```

Three GATEs — places where the skill calls `AskUserQuestion`. Note: skills, like slash commands, run in the main session and *can* call `AskUserQuestion`. Only subagents can't.

**Stage 0 — Pre-checks.** `git rev-parse --show-toplevel` to confirm we're in a git repo (so the output dir is sensible).

**Stage 1 — Attach.** A three-option `AskUserQuestion` (`SKILL.md:50–60`):

```
question: "How do you want to attach to Chrome?"
options:
  - "Open a new Chrome window": Closes any prior Playwright Chrome and launches a fresh one.
  - "Use Chrome that's already open — paste the URL": Reuses the running Playwright Chrome (preserves SSO state).
  - "Cancel": Exit.
```

Branch B preserves authenticated sessions:

> **Do NOT call `browser_close`** in this branch — closing destroys the existing session and defeats the purpose. (`SKILL.md:91`)

And there's an explicit no-auto-recover rule:

> Do NOT silently `browser_close` and retry — the user picked this branch specifically to preserve their authenticated session, and that session is gone. (`SKILL.md:102`)

If the existing Chrome died, fail loudly. Don't try to "fix it" by opening a new window — that's the opposite of what the user asked for.

**Stage 2 — Ready.** Confirm the user has navigated / authenticated. Capture `URL` and `PAGE_TITLE` via `browser_evaluate`. Compute the run dir from a URL slug.

**Stage 3 — Scan.** This is where axe runs. The actual MCP call (`SKILL.md:158–179`):

```javascript
mcp__plugin_a11y_playwright__browser_evaluate
  function: "async () => {
    if (typeof window.axe?.run !== 'function') {
      return { error: 'axe-core not loaded — init-script may have failed' };
    }
    const r = await window.axe.run({
      runOnly: { type: 'tag', values: ['wcag2a', 'wcag2aa', 'wcag21aa'] },
      resultTypes: ['violations', 'incomplete']
    });
    return {
      axeVersion: window.axe.version,
      url: location.href,
      title: document.title,
      timestamp: new Date().toISOString(),
      violations: r.violations,
      incomplete: r.incomplete,
      passes: r.passes.map(p => ({ id: p.id })),
      inapplicable: r.inapplicable.map(i => ({ id: i.id }))
    };
  }"
```

Two design choices worth lingering on:

1. **`typeof window.axe?.run !== 'function'`** — the skill checks if axe is actually present on the page. If not, it returns a structured error and the skill aborts with a recovery hint. The check is *defensive*: even though the MCP server's `--init-script` should have injected axe, the skill assumes it might fail.
2. **Inline result, no `filename:`** — the skill explicitly tells you not to pass `filename:`:
   > Do **not** pass `filename:`. The result returns inline (~30–50 KB JSON, well within the inline limit thanks to `resultTypes` + the `.map()` projections). Use it directly from the tool response. (`SKILL.md:181`)

   The `.map()` projections (`passes.map(p => ({ id: p.id }))`) drop the verbose per-pass node lists, keeping JSON size manageable. The full violations and incomplete arrays come back inline.

Then a screenshot:

```
mcp__plugin_a11y_playwright__browser_take_screenshot
  type: "png"
  fullPage: true
  filename: $RUN_DIR/page.png
```

Failure here is non-fatal — log and continue.

**Stage 4 — Preview + Decide.** The skill prints a chat-side summary of the top 5 violations *before* asking whether to generate the slow HTML report. The truncation rules are explicit (`SKILL.md:236–244`):

> | Field | Source | Rule |
> | --- | --- | --- |
> | `target` | `violation.nodes[0].target.join(" ")` | Truncate to **120 chars**, ellipsis if longer. |
> | `source` | `violation.nodes[0].html` | Truncate to **200 chars**, ellipsis if longer. |
> | `failure` | `violation.nodes[0].failureSummary` | Strip the leading `Fix any of the following:` prefix. Take the first line only. Truncate to **240 chars**. |

This is a skill *teaching* the LLM how to format chat output. The LLM is going to print these strings; the skill lays down the truncation rules so the output stays consistent across runs.

Then the gate:

```
question: "Generate the interactive HTML report?"
options:
  - "Yes — generate the report": Build the full report. (Takes longer.)
  - "No — stop here": Keep the in-chat summary and the screenshot file.
```

**Stage 5 — Report (conditional).** If the user said yes:

1. **MANDATORY** read of `references/report-format.md` (`SKILL.md:272–276`):

   > ### 5.1 Read the spec — MANDATORY before writing any HTML
   >
   > ```
   > Read
   >   file_path: ${CLAUDE_PLUGIN_ROOT}/skills/a11y-browser-verify/references/report-format.md
   > ```
   >
   > The spec defines every layout decision: section order, REPORT_DATA shape, color tokens, typography stack, summary-card behaviour, modal pattern, expandable detail, color-contrast detail block, empty state, footer. **Follow it. Do not invent your own structure.**

   This is the same "mandatory-first-action read" pattern from agents — applied to skills. The HTML format is an editable contract, not something the LLM should improvise. If you change `report-format.md`, the next run picks up the new format.

2. Build a `REPORT_DATA` object from the axe result.

3. **`Write`** (not Bash heredoc) the full self-contained HTML to `$RUN_DIR/report.html`:

   > All CSS + JS inline. No remote loads except the sibling `page.png`. Embed `REPORT_DATA` as `const REPORT_DATA = {...};` inside a `<script>` at the top of `<body>`. (`SKILL.md:299`)

4. Offer to `Start-Process` / `open` / `xdg-open` the report for the user.

### Rules — explicit don'ts

`skills/a11y-browser-verify/SKILL.md:352–364`:

> - ✅ Capture axe result inline via `browser_evaluate` — **no `filename:` argument**.
> - ✅ Read `references/report-format.md` **before** writing `report.html`.
> - ✅ Use the **Write tool** for `report.html` (not Bash heredoc).
> - ❌ Do NOT save axe data to any file.
> - ❌ Do NOT parse axe data via `grep`, `awk`, `sed`, `python`, `python3`, `node -e`, or `cat | jq`.
> - ❌ Do NOT read from `~/.claude/projects/**/tool-results/`.
> - ❌ Do NOT design the report layout from prior knowledge — the spec is the contract.
> - ❌ Do NOT attach click handlers to summary cards with count = 0 (cards are inert at the DOM level).
> - ❌ Do NOT render the `Show Saffron Alternative` row when `saffronAlternative` is undefined (Phase 1 → never).

The "do NOT parse axe data via grep/awk/sed/python" rule is unusual — what would *cause* an LLM to do that? Answer: panic. If the JSON is large, the LLM might try to `grep` for "violations" in saved file output. The rule pre-empts that: keep the data inline, parse it as JS, write the HTML directly. Don't attempt CLI gymnastics.

## Asset vendoring: how axe-core gets injected

This is the elegant part. Axe-core (~280 KB minified) is bundled with the plugin. It's never downloaded at runtime. It's injected into every page Playwright navigates to.

### The MCP server config

`.mcp.json:14–22`:

```json
"playwright": {
    "command": "npx",
    "args": [
        "-y", "@playwright/mcp@latest",
        "--browser", "chrome",
        "--ignore-https-errors",
        "--init-script", "${CLAUDE_PLUGIN_ROOT}/scripts/axe.min.js"
    ]
}
```

Three flags:

| Flag | Effect |
| --- | --- |
| `--browser chrome` | Use the user's installed Chrome (not the bundled Chromium). The skill will fail at attach time if Chrome isn't installed. |
| `--ignore-https-errors` | Dev / staging / VPN-internal sites with self-signed certs are common; ignore-errors lets axe scan them. |
| `--init-script <path>` | Run this JS in every page context as soon as it loads, before any page script. The plugin points it at the bundled `axe.min.js`. |

### Why this is bundled, not from CDN

`scripts/README.md:7–14`:

> ## Why vendored, not from a CDN
>
> - Works offline / in air-gapped environments
> - No dependency on external CDN availability or TR network policy on cdnjs/jsdelivr
> - Reproducible: a given plugin version pins a specific axe rule set
> - Travels with the plugin via `${CLAUDE_PLUGIN_ROOT}` — referenced by absolute path in `.mcp.json`, no relative-path or sibling-folder fragility

Pinning version 4.11.4 means a future axe release with rule changes doesn't silently shift behaviour. Bundling means a corporate firewall can't break the plugin. Using `${CLAUDE_PLUGIN_ROOT}` means the path resolves correctly from any working directory.

### Refreshing axe

`scripts/README.md:21–30`:

```bash
npm pack axe-core@latest
tar -xzf axe-core-*.tgz
cp package/axe.min.js a11y-workflow-marketplace/plugins/a11y/scripts/axe.min.js
rm -rf package axe-core-*.tgz
```

Standard "vendor the file from npm and commit it" flow. Bump the version row in `scripts/README.md` and the plugin's `version` in `plugin.json`.

### The detection check

The skill verifies axe loaded successfully by checking for `window.axe.run`:

```javascript
if (typeof window.axe?.run !== 'function') {
  return { error: 'axe-core not loaded — init-script may have failed' };
}
```

If the init-script silently failed (path didn't resolve, plugin cache out of sync, etc.), this check trips immediately on Stage 3. The skill aborts with a recovery instruction:

> Verify `${CLAUDE_PLUGIN_ROOT}/scripts/axe.min.js`; `/reload-plugins`. Abort. (`SKILL.md:378`)

## Reasoning helpers: `expert`, `lint`, `ux`, `test`, `localize`

These five skills are *not* meant to be invoked as slash commands. They're loaded contextually by the developer agent when reviewing code or editing files.

### `expert/SKILL.md`

`skills/expert/SKILL.md:1–4`:

```yaml
---
name: expert
description: Expert code quality rules for accessibility (WCAG 2.1 AA), architecture (dependency direction, layering, SOLID), simplicity (YAGNI, redundancy), readability (cognitive complexity, nesting, comprehension), performance (complexity, memory, caching, network), security (XSS, OWASP, secrets), and frontend quality (naming, imports, modern patterns, testability). This skill should be used when writing, reviewing, or refactoring code to ensure compliance with accessibility standards, architectural integrity, code simplicity, readability, performance efficiency, application security, and frontend code quality.
---
```

The body is a directory of pointers (`skills/expert/SKILL.md:62–73`):

> ## How to Use
>
> Read individual rule files for detailed guidance:
>
> ```
> rules/a11y.md
> rules/architecture.md
> rules/simplicity.md
> rules/readability.md
> rules/performance.md
> rules/security.md
> rules/frontend.md
> ```
>
> Each rule file contains:
>
> - Core principles and guidelines
> - Specific checks and verification criteria
> - Output format for reporting findings

The skill body itself is short — it lists the 7 rule categories and points at the sub-files. The actual rules live in `rules/<category>.md`. When the developer agent decides "I'm refactoring; let me apply the architecture rules," it loads `rules/architecture.md` directly.

### Why split rules into sub-files

If you put all the rules in one big SKILL.md, the agent loads everything just to apply one category. By keeping each category as `rules/<name>.md`, the agent can grep for and load only the relevant subset.

The pattern is "skill body = TOC; rules = leaves." It scales as the rule set grows.

### `ux/SKILL.md` — script-augmented skills

The `ux` skill validates that newly-added CSS/SCSS uses Saffron tokens instead of hardcoded values. Its body is a TOC plus *script invocations*.

For colors, the rule is implemented as a Node script (`skills/ux/scripts/check-colors.mjs`). The skill spawns it via Bash:

```bash
node .claude/skills/ux/scripts/check-colors.mjs --color [additional flags]
```

The script does the heavy lifting:

- Reads the git diff (`git diff main...HEAD -- '*.css' '*.scss'`).
- Extracts hex values from added lines.
- Loads Saffron tokens from `node_modules/@saffron/core-styles/dist/tokens/variables.css`.
- Computes CIEDE2000 colour-difference between each hex value and each token.
- Classifies each finding into 4 tiers (EXACT, CLOSE, SIMILAR, UNRECOGNIZED).
- Prints ANSI-coloured output with optional 24-bit colour swatches.

The skill body just orchestrates: it parses arguments, runs the script with the right flags, and reports results. The CIEDE2000 math doesn't need to be in the skill prompt — the LLM doesn't need to *understand* the algorithm, it just needs to know *when* to run the script.

This is the **"skill = lightweight orchestration; script = heavy lifting"** pattern. Three skills in this plugin use it:

| Skill | Script | Purpose |
| --- | --- | --- |
| `ux` | `scripts/check-colors.mjs` | CIEDE2000 colour-difference vs Saffron tokens |
| `lint` | `scripts/ts-type-check.mjs` | Walk up to the right `tsconfig.json` and run `tsc --noEmit` |
| `test` | `scripts/find-test-config.mjs` | Locate Jest / Karma / Jasmine config from a file path |

When you write a complex algorithm (CIEDE2000 colour math, AST traversal, file system walking), don't try to express it in the skill prompt. Vendor a JS / Python / shell script and have the skill invoke it.

## When to make a skill user-invokable vs reasoning helper

The two patterns in this plugin are nicely contrasted:

| | User-invokable | Reasoning helper |
| --- | --- | --- |
| Example | `a11y-browser-verify` | `expert`, `lint`, `ux`, `test`, `localize` |
| Invoked by | The user, typing `/a11y:<name>` | The developer agent, deciding contextually |
| Has gates? | Yes — `AskUserQuestion` calls in the skill body | Rarely |
| Drives MCP servers? | Yes — Playwright | No |
| Writes user-visible artifacts? | Yes — HTML reports, screenshots | No — just informs the agent's reasoning |
| `description` style | Keyword-rich, multiple synonyms ("audit a page", "scan for violations") | Category-list ("rules for accessibility, architecture, simplicity...") |
| Body | Long step-by-step pipeline | Short TOC + sub-file references |

Decide based on whether the artifact is *for the user* or *for the agent*:

- **For the user** → user-invokable skill. They invoke it; it produces an output (report, screenshot, file diff) they consume.
- **For the agent** → reasoning helper. The agent invokes it during another task; the output never leaves the agent's context.

---

## Skill loading vs slash command — a subtle distinction

Both skills and slash commands can run in the main session. Both can call `AskUserQuestion`. Both can use any tool. So when does it matter which you write?

A slash command is **always invoked by name** (`/foo`). The user types it; it runs.

A skill is **invoked by relevance**. Claude considers all skills in scope, scores them by description match against the user's request, and loads the most relevant one. User-invokable skills can also be triggered as slash commands by the harness convention `/<plugin>:<skill-name>` — but that's an alias, not the skill's primary mode.

Reasoning-helper skills are *only* loaded by relevance scoring. They have no slash command surface; you can't type `/a11y:expert` and get a useful interaction.

In practice:

- **Use a slash command** when the workflow is named, well-defined, and orchestrator-shaped (`/a11y:investigate`, `/a11y:developer`, `/a11y:ship`).
- **Use a user-invokable skill** when the workflow is more of a "ad-hoc tool" the user invokes by topic ("audit this URL", "scan for WCAG violations").
- **Use a reasoning-helper skill** when you want an *agent* to load specialized rules / guidance contextually during a longer task.

## Checklist: designing a skill

If you're authoring `your-plugin/skills/<name>/SKILL.md`:

1. **Decide the role.** User-invokable or reasoning helper? Different `description` style.
2. **Frontmatter.** `name`, `description` (keyword-rich for user-invokable; category-list for reasoning helpers), `argument-hint` if user-invokable.
3. **Decide the structure.**
   - Linear pipeline (browser-verify): step-by-step instructions in `SKILL.md`.
   - Catalog (expert): TOC in `SKILL.md`, leaves in `rules/<name>.md`.
   - Script-augmented (ux): TOC + Bash invocations of vendored scripts.
4. **For user-invokable skills with external dependencies (browser, DB, etc.):**
   - Pre-checks at the start. Verify dependencies exist.
   - Explicit gates via `AskUserQuestion` for user decisions.
   - Recovery rules — when to retry, when to abort, when not to "auto-fix" (preserve the user's session).
   - Output dir under `<project>/.<plugin>/<sub-folder>/<timestamp>-<slug>/`.
5. **For reasoning helpers:**
   - Keep `SKILL.md` short.
   - Put detailed rules in `rules/<name>.md` so the agent can grep + load selectively.
   - Use `references/<name>.md` for long-form prose (algorithm explanations, framework comparisons).
6. **For script-augmented skills:**
   - Vendor the script in `scripts/<name>.mjs`.
   - SKILL.md says "run `node .claude/skills/<skill>/scripts/<script>.mjs <flags>`" — let the script handle the algorithm.
7. **Output contract.** If the skill writes an artifact (a report, a file), pin the format in `references/<format-name>.md` and have the skill body say "Read this file before writing." Same pattern as agents reading their field templates.
8. **Vendored assets via `--init-script` (advanced).** For skills that need a JS library injected into pages by an MCP server, bundle the library in `scripts/<name>.min.js` and reference it as `${CLAUDE_PLUGIN_ROOT}/scripts/<name>.min.js` in `.mcp.json`'s server args.
