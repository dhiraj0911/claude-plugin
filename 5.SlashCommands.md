# 05 — Slash commands: orchestrators that own user gating + git

> Slash commands run in your main Claude Code session. Subagents run in isolated sub-contexts. Only the slash command can call `AskUserQuestion`. That single fact shapes the entire orchestration design.

---

## What a slash command is

A slash command is a markdown file in `commands/<name>.md`. Its frontmatter is metadata; its body is *instructions to Claude in your main session* — what to parse from `$ARGUMENTS`, what tools to call, what to do with the results.

When you type `/a11y:developer 2341709`, Claude Code:

1. Locates `plugins/a11y/commands/developer.md`.
2. Substitutes `$ARGUMENTS` with `2341709`.
3. Streams the file's body into your main conversation as instructions.
4. Claude (in your main session) follows those instructions, with full access to all tools you've authorised.

Critically: **the slash command's instructions are executed by Claude in your main session, not by a subagent.** That's the difference between commands and agents in this codebase. Subagents have isolated contexts and cannot call `AskUserQuestion`. The main session can. So all user gates go in slash commands, never in agents.

The plugin defines three:

| Command | Frontmatter `description` (excerpt) |
| --- | --- |
| `/a11y:investigate <id>` | "Spawns the a11y-investigator agent to classify the bug, analyse attachments, consult the knowledge base, and produce a complete work order in the bug folder for the downstream developer. With --chat, opens an interactive edit session against an existing run-state.json without spawning the agent." |
| `/a11y:developer <id>` | "The slash command IS the orchestrator — it runs in the main session (so AskUserQuestion works), creates the fix branch, spawns the autonomous a11y-developer worker, then presents the resulting diff to the user for approval." |
| `/a11y:ship <id>` | "Spawns the a11y-shipper agent to draft the commit + PR body, stage explicit files, commit, push, and open a draft PR." |

---

## Frontmatter: minimal

`commands/ship.md:1–4`:

```yaml
---
description: Ship an accessibility fix produced by the developer. Spawns the a11y-shipper agent to draft the commit + PR body, stage explicit files, commit, push, and open a draft PR. PRs are always drafts — humans review and promote to ready-for-review.
argument-hint: '<bug-id>'
---
```

That's it. Two fields. `description` is shown in `/help` and used for relevance scoring; `argument-hint` is help text shown next to the command name.

The command bodies do all the real work. They're 70–352 lines (ship is short, developer is long) of step-by-step instructions for Claude to execute.

## Argument parsing

Each command parses `$ARGUMENTS` itself — there's no auto-parsing. The instructions tell Claude how to handle the string.

### Simple case — `ship.md`

`commands/ship.md:8–14`:

> ## Step 1 — Parse arguments
>
> From `$ARGUMENTS`:
>
> - **Bug ID** — the first token. Strip any leading `AB#` prefix. Keep the numeric digits only.
>
> If the bug ID is missing or non-numeric after stripping `AB#`, stop and ask the user for a valid bug ID.

Two rules: strip `AB#`, validate it's numeric, refuse cleanly if not.

### Multi-flag case — `developer.md`

`commands/developer.md:8–17` is more involved:

> ## Step 1 — Parse arguments
>
> From `$ARGUMENTS`:
>
> - **First positional arg:**
>     - If matches `^AB?#?\d+$` (digits, optionally with `AB#` prefix) → strip `AB#`, treat as `BUG_ID`.
>     - Otherwise → treat as `AD_HOC_DESCRIPTION` (free-text).
> - **Flags** (any order):
>     - `--dom "<html>"` → DOM snippet hint. Passed to the agent as `HINT_DOM`.
>     - `--revise "<text>"` → post-completion touch-up. Mutually exclusive with all other flags except plain bug-ID.

Then a flag-conflict table (`commands/developer.md:21–25`):

> ## Step 2 — Validate flag conflicts (refuse cleanly)
>
> | Combination | Action |
> | --- | --- |
> | `--revise` + `--dom` | Refuse: `"--revise doesn't combine with scope hints. The prior run's scope is reused."` |
> | Ad-hoc + `--revise` | Refuse: `"Ad-hoc mode (no bug-ID) cannot revise — there's no prior run."` |
> | Ad-hoc + no `--dom` | Refuse: `"Ad-hoc mode requires --dom (the agent needs grounding)."` |
>
> If any refusal: print the message and stop. Do NOT spawn the agent. Do NOT touch git.

Two design choices worth naming:

1. **The slash command refuses early.** Bad combinations don't spawn the agent and don't touch git. The agent is a heavy operation; cheap refusals at the orchestrator level save time and money.
2. **Refusal text is exact.** Each row has a literal error message. The instructions don't say "explain the conflict" — they say "use this exact string." That's because slash command authors care about UX consistency: if the same orchestrator handles fifteen flag combinations, the refusal language should be uniform.

### Mutually exclusive modes — `investigate.md`

`commands/investigate.md:13–19`:

> - `--bg` → run the agent in the background.
> - `--resume` → re-run on an existing folder; investigator skips cached phases per its own logic.
> - `--clarify "<answer>"` → append `<answer>` as a user clarification.
> - `--chat` → open an interactive edit session against an existing `run-state.json`. **Does NOT spawn the agent.** Mutually exclusive with `--bg`, `--resume`, and `--clarify`.

`--chat` is qualitatively different from the other three flags — it bypasses the agent entirely and runs as edit instructions in the main session. Listing the mutual exclusion in the frontmatter description ("With --chat, opens an interactive edit session against an existing run-state.json without spawning the agent") makes the divergent behaviour discoverable.

## Spawning the worker

All three commands use the `Agent` tool with a minimal delegation prompt. The pattern is consistent: pass `RUN_DIR`, pass any flags as named lines (`HINT_DOM`, `REVISE`, `RESUME`, `CLARIFY`), and append the agent's standing entry instructions.

`commands/investigate.md:99–131`:

> Use the `Agent` tool:
>
> - `subagent_type`: `"a11y:a11y-investigator"`
> - `description`: `"Investigate AB#<id>"`
> - `run_in_background`: `true` if `--bg` was passed, otherwise `false`
> - `prompt`: build from the template below, including only the flag lines that apply.
>
> #### Delegation prompt (build from this template)
>
> ```
> Investigate bug AB#<id>.
>
> RUN_DIR: <RUN_DIR>
> ```
>
> If `--resume` was passed, append:
>
> ```
> RESUME: true
> ```
>
> If `--clarify "<answer>"` was passed, append:
>
> ```
> CLARIFY: <answer>
> ```
>
> Finally append:
>
> ```
> Read <RUN_DIR>/run-state.json if it exists; otherwise initialize the folder and state.
> Follow your 9-phase discovery flow. Return the single-line confirmation.
> ```
>
> Keep the prompt minimal. Do not embed schema, template content, or knowledge references — the agent reads those itself.

The last sentence is critical:

> Keep the prompt minimal. Do not embed schema, template content, or knowledge references — the agent reads those itself.

This is a discipline. The slash command could *easily* paste the entire `investigator-field-template.md` into the spawn prompt. It deliberately doesn't. The agent reads the template itself, every run, from `${CLAUDE_PLUGIN_ROOT}/knowledge/`. Two reasons:

1. **Single source of truth.** Edit `investigator-field-template.md`, every run picks it up. No risk of "the slash command embedded an old version."
2. **Cheap context.** The delegation prompt stays tiny. The agent's *first action* fetches the schema. If the schema changes, no slash command edit is needed.

Doc 09 lists this as part of pattern 5 (Output contract as edited file).

## The diff-review gate — the centerpiece

`/a11y:developer` is the only command with a user gate. It's where the orchestrator pattern shines.

After the developer agent returns, the slash command (`commands/developer.md:135–267`) reads the new `run-state.json`, runs `git diff main..HEAD`, presents a structured summary, and asks via `AskUserQuestion`:

`commands/developer.md:191–199`:

> ### 8c. Ask the user
>
> Use `AskUserQuestion`:
>
> | Option | Effect |
> | --- | --- |
> | **Approve** | Stage explicit files, commit, record SHA in run-state. The user's next step is `/a11y:ship <id>`. |
> | **Request adjustments** | Prompt for free-text revision request. Re-spawn the agent with `--revise "<text>"` against the SAME branch. Cap at 3. |
> | **Discard** | Save a forensic patch, restore files (or reset HEAD if the developer's commit-on-approve already ran on a prior pass), delete the branch, mark run `aborted`. |

Three options. Three branches. Each does something profoundly different to git and to `run-state.json`.

### On Approve

`commands/developer.md:203–267`:

1. **Draft the commit message** from `bug.title` + `bug.a11y.wcag` + `development.approach.summary`. Cap at 72 chars on the subject. Add `Co-Authored-By: Claude Opus`.
2. **Stage explicit paths** — never `git add -A`:
   ```bash
   git add <each path in development.filesChanged.{source,tests,new}>
   ```
3. **Commit with `--no-verify`** — Step 6 in the agent already ran lint and test:
   ```bash
   git commit --no-verify -m "$(cat <<'EOF'
   <full commit body>
   EOF
   )"
   ```
4. **Capture the SHA** and write it back into `run-state.json`:
   ```
   development.userChoices.diffReview = "approved"
   development.commit = { sha, subject, committedAt }
   ```
5. Tell the user: *"Committed. Next: run `/a11y:ship <id>` to push and create the draft PR."*

The implementation notes section explains *why* this design (`commands/developer.md:347–351`):

> - **Why commit on Approve (here) instead of in the shipper:** parallelism. Multiple `/a11y:developer` runs on different bugs each commit on their own branch in their own slash-command session; nothing serializes through a single shipper.
> - **Why `--no-verify` on commit:** Step 6 in the developer agent already runs lint and test. The pre-commit hook in most repos runs the same checks. Skipping the hook avoids spawn-failure issues in environments where the hook script is misconfigured.

### On Request adjustments

`commands/developer.md:271–281`:

> Prompt for the user's free-text revision request. Append to `userChoices.revisions[]`:
> ```
> { trigger: "diff-review", request: "<text>", at: "<ISO>" }
> ```
> `Write` the run-state.
>
> Re-spawn the `a11y-developer` agent with the SAME `RUN_DIR` and `REVISE: <text>` in the prompt. The agent reuses the branch (it's still checked out) and applies only the user's revision request. After the second agent return, loop back to Step 7 → Step 8 (read diff again, re-present).
>
> After 3 revisions in one session, force the user to Approve or Discard — no further adjustments.

Two design choices:

1. **Revisions are logged.** Every adjustment goes into `userChoices.revisions[]` with the trigger ("diff-review" vs `--revise` direct invocation), the user's exact request text, and a timestamp. So the audit trail captures *what* the user asked for, not just *that* they asked.
2. **Revision cap is 3.** No infinite loops. Three iterations is enough for a small adjustment; if you need more, the diff is fundamentally wrong and Discard + start-over is cheaper.

### On Discard

`commands/developer.md:283–315`:

```bash
TS=$(date -u +%Y%m%dT%H%M%SZ)
git diff main..HEAD > <RUN_DIR>/rejected-diff-${TS}.patch
```

> The diff between `main` and the fix branch's tip captures everything regardless of whether the developer's edits are committed (a prior Approve already ran 8d.2) or still uncommitted (no Approve yet). Save it for forensics.
>
> Then nuke the branch — this removes both uncommitted edits and any commit on it:
>
> ```bash
> git checkout main
> git branch -D <branch>
> git status --short  # MUST be clean
> ```

Then update `run-state.json`:

```
development.status = "aborted"
development.userChoices.diffReview = "discarded"
development.revert = { files: [...], patchPath: "<RUN_DIR>/rejected-diff-<TS>.patch" }
development.branch = null
development.commit = null
runMeta.phase = "aborted"
```

Two design choices:

1. **Always save a forensic patch BEFORE deleting the branch.** Discarded work is not lost — it's archived as a `.patch` you can `git apply` if you change your mind tomorrow. The patch path is recorded in `revert.patchPath`.
2. **`branch = null` and `commit = null` after Discard.** Re-running `/a11y:developer <id>` after Discard sees no prior development slice and starts fresh, on a fresh branch.

## Git lifecycle ownership

The pattern across all three commands:

| Action | Who does it | Where |
| --- | --- | --- |
| Validate working tree is clean | `developer` slash command | Step 4b — `git status --porcelain && git branch --show-current` |
| `git checkout main && git pull` | `developer` slash command | Step 5a |
| `git checkout -b fix/AB#<id>-<short>` | `developer` slash command | Step 5a |
| Edit source files | `a11y-developer` agent | Step 5 of the agent |
| `git add <explicit paths>` | `developer` slash command | Step 8d.2 (on Approve) |
| `git commit --no-verify` | `developer` slash command | Step 8d.2 (on Approve) |
| Save forensic `.patch` | `developer` slash command | Step 8d.3 (on Discard) |
| `git branch -D` | `developer` slash command | Step 8d.3 (on Discard) |
| `git push -u origin <branch>` | `a11y-shipper` agent | Step 3a (the agent uses Bash) |
| `gh pr create --draft` | `a11y-shipper` agent | Step 3b |

The split: **the developer slash command owns local git mutations**, **the shipper agent owns remote git mutations** (push and PR creation).

Why is the shipper allowed to do remote git mutations when the developer agent isn't allowed to do local ones? Because the shipper's spec is much narrower. It only does push + draft PR. It can't go off-script and start `git rebase`-ing things, because the system prompt says (`agents/a11y-shipper.md:103`):

> `-u` sets upstream the first time. NEVER force-push.

And (`agents/a11y-shipper.md:186`):

> **NEVER:** `git push --force` / force-push.

The shipper has narrow git authority because it has narrow git purpose. The developer has even narrower authority (zero git) because it has broader source authority — and you don't want broad-source-authority and broad-git-authority in the same agent context.

## Phase-lock validation in commands

The slash commands check the phase lock too — defence in depth on top of the agent's own check.

`commands/developer.md:48–54`:

> ### 4a. Validate `<RUN_DIR>/run-state.json`
>
> Use `Bash` to check that `<RUN_DIR>/run-state.json` exists. Then `Read` it.
>
> | Mode | Required state |
> | --- | --- |
> | Bug-ID (canonical) | `runMeta.phase == "ready-for-developer"` AND `decision.status == "ready-to-proceed"` |
> | `--revise` | Prior `development.*` exists with `status` of `ready-for-verify` or `aborted` |
> | Ad-hoc | File may not exist yet; agent will seed it. `<RUN_DIR>` must exist (Step 3 created it). |
>
> On precondition failure: print a clear message, suggest the corrective action (`/a11y:investigate <id>` first, or use the right mode), and stop. Do NOT spawn the agent. Do NOT touch git.

Three modes, three different precondition checks. The orchestrator refuses *before* it spawns the agent. The agent will refuse *again* in its own Step 1b — the duplication is intentional. Two layers means a misconfiguration in either layer doesn't let bad input through.

## Background mode (`--bg`) — investigate only

The investigator supports background runs (`commands/investigate.md:103, 137`):

> - `subagent_type`: `"a11y:a11y-investigator"`
> - `run_in_background`: `true` if `--bg` was passed, otherwise `false`

> If `--bg` was passed: the Agent tool returns immediately. Tell the user: _"Investigator started in background for AB#<id>. State at `<RUN_DIR>/run-state.json`. You'll be notified when it finishes."_ Stop here.

Background runs require the user to **pre-accept tool permissions** — otherwise the agent will hit a prompt mid-run and hang silently. `docs/state.md:122–144` covers the permission allowlist for `--bg`. The setup-guide bullet list goes broader still — full Read/Write/Edit auto-approve for background jobs, more conservative for interactive runs.

The developer and shipper don't have `--bg`. The developer can't, because it has a user gate after the agent returns; the shipper can't, because it's a fast operation that doesn't need backgrounding. Only the investigator is slow enough and gate-free enough to benefit.

## `--chat` — bypass the agent entirely

The investigator's `--chat` mode is unusual: the slash command instructs Claude to **act as the agent** in the main session, with strict rules.

`commands/investigate.md:34–96`:

> ### Step 3a — Chat mode (no agent spawn)
>
> 1. **Verify the run exists (strict).** [...]
>
> 2. **Load context into the main session.** In parallel:
>     - `Read <RUN_DIR>/run-state.json`
>     - `Read ${CLAUDE_PLUGIN_ROOT}/knowledge/investigator-field-template.md`
>
> 3. **Print a compact summary** so the user knows what they're editing.
>
> 4. **Enter chat mode.** [...]
>
> #### Step 3a Rules — how to edit `run-state.json` in chat mode
>
> 1. **Use `Edit` directly on `<RUN_DIR>/run-state.json`.** Do not spawn an agent.
> 2. **Respect the output contract** in `investigator-field-template.md` [...]
> 3. **Auto-derive related fields from the knowledge base.** When the user changes a primary classification field, grep the knowledge base and update dependent fields in the same edit cycle [...]
> 4. **Auto-flip `decision.status` with confirmation.** If the user's edit resolves the active `decision.gateReason` [...]
> 5. **Log every edit to `additionalNotes[]`.** Append a one-line entry per edit [...]
> 6. **Do NOT change `runMeta.phase`.** Chat is a side channel, not a phase transition.
> 7. **Do NOT spawn agents, run git, open a browser, or edit source code.**

This mode lets a user repair an investigator's mistake conversationally — say "the product is Westlaw Edge, not Carswell" — without re-running the agent. The orchestrator does the JSON edits, respecting the field template, auto-deriving dependent fields (e.g., when product changes, regrep `products.md` and update `productDir`), and logging every edit to `additionalNotes[]` for audit.

The pattern: **the slash command is itself a richer surface than just "spawn an agent."** Sometimes it spawns; sometimes it acts. `--chat` is the "act" mode for the investigator. There's no agent equivalent because the LLM in the main session has full freedom to use `AskUserQuestion`, follow up on user replies, and run several tool calls in sequence — none of which a sub-agent can do as cleanly.

## `--revise` — re-spawn against the same branch

The developer command's `--revise` flag is a way to apply a small touch-up to an existing run without starting over (`commands/developer.md:87–91`):

> ### 5b. `--revise`
>
> Already on the prior branch (Step 4b ensured it). Nothing to create.
>
> If the orchestrator detects the branch doesn't exist (e.g., user ran a prior Discard that deleted it): refuse with `"Prior branch <name> not found — was the prior run discarded? Run a fresh /a11y:developer <id> to start over."`

And the agent's `--revise` mode skips Steps 2–4 (`agents/a11y-developer.md:494–500`):

> ### `--revise`
>
> - Steps 1a, 1b, 1c run normally. Steps 2, 3, 4 SKIPPED.
> - Step 1c reads current disk state of prior `filesChanged.source[]` (user may have edited manually).
> - Step 5 applies ONLY the user's `revisionRequest`. No re-reasoning.
> - Step 6 self-check still runs.
> - Step 7 final write — append to `userChoices.revisions[]`; preserve prior-run fields.

Use case: the developer made a fix that's almost right. You don't need fresh discovery and Saffron consultation; you just want to swap one ARIA attribute. `--revise "use aria-label not aria-labelledby"` does the targeted change, runs lint/test again, and re-presents the diff. Cheap.

## "Implementation notes" — design rationale at the bottom

`commands/developer.md` ends with a short rationale section (`commands/developer.md:344–352`):

> ## Implementation notes
>
> - **Why orchestrator owns the gate:** `AskUserQuestion` is unavailable inside subagents. Putting the gate in this slash command (which runs in the main session) is the only architecturally sound way to make the user gate actually fire.
> - **Why review the diff, not the plan:** users review what was actually written, not a pre-implementation plan that may not match the result. Cheaper signal, fewer false approvals.
> - **Why commit on Approve (here) instead of in the shipper:** parallelism. [...]
> - **Why `--no-verify` on commit:** Step 6 in the developer agent already runs lint and test. [...]
> - **Why no worktree:** simpler — branch on main checkout, agent edits files there. On Discard, `git restore` + `git branch -D` cleans up.
> - **Why the agent never commits:** the developer's contract is "edit files + persist state." The shipper owns commit + push + PR.

Worth borrowing the practice. Closing your slash command with "why we made these specific choices" lets the next maintainer (which may be your future self) understand the constraints. When someone asks "why don't we just commit in the shipper?", the answer is in the file.

## Checklist: designing a slash command

If you're authoring `your-plugin/commands/<name>.md`:

1. **Frontmatter**
   - [ ] `description` summarises what this command does and any non-obvious behaviour (e.g., "with --chat, opens an interactive edit session").
   - [ ] `argument-hint` shows the expected positional + flags.

2. **Body structure**
   - [ ] Step 1: parse arguments. State the rules; refuse cleanly on bad input.
   - [ ] Step 2: validate flag conflicts (if any). Refuse with explicit messages.
   - [ ] Step 3: compute paths. `git rev-parse --show-toplevel` for project root, then `<root>/.<plugin>/<run-folder>/`.
   - [ ] Step 4: validate prior state (file exists? phase lock? git tree clean?).
   - [ ] Step 5: do any pre-spawn setup (branch creation, folder creation).
   - [ ] Step 6: spawn the agent via `Agent` tool. Keep the prompt minimal — no embedded schema.
   - [ ] Step 7: read state after the agent returns.
   - [ ] Step 8: gate the user via `AskUserQuestion` (if applicable). Map each option to an exact effect on git + state.
   - [ ] Step 9: print a final summary.
   - [ ] Step 10: print a next-step hint based on terminal status.

3. **What to refuse early** (cheaper than spawning the agent and refusing later)
   - [ ] Bad arguments.
   - [ ] Conflicting flags.
   - [ ] Wrong phase lock.
   - [ ] Dirty working tree (when about to do branch work).
   - [ ] Missing prior run (when current command depends on it).

4. **Mode flags to consider**
   - [ ] `--bg` for long-running tasks where the user can walk away.
   - [ ] `--resume` for re-running an existing run with cached intermediate state.
   - [ ] `--chat` for editing state conversationally without re-running the agent.
   - [ ] `--revise` for re-spawning the agent against the same artifacts with a delta.

5. **Implementation notes section at the bottom**
   - [ ] Brief explanation of *why* you made the architectural choices.
