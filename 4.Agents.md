# 04 — Agents: designing autonomous subagents

> A subagent is a markdown file. Its frontmatter declares what it can do; its body is the system prompt that tells it how. This is where most of the plugin's design discipline lives.

---

## What a subagent is

In Claude Code, the `Agent` tool spawns a sub-context: a fresh conversation, a separate system prompt, its own tool allowlist, and a separate token budget. The parent (slash command, or another agent) hands it a prompt; it runs to completion; it returns one message.

You define a subagent by dropping a markdown file in `agents/<name>.md`. The frontmatter is metadata; the body is the system prompt. That's it — no class hierarchy, no IDE-specific "agent runner," no plugin API.

This plugin defines three:

| File | Role |
| --- | --- |
| `agents/a11y-investigator.md` | Strategic locator. Reads ADO + screenshots + knowledge base. Produces a work order. Cannot edit source. |
| `agents/a11y-developer.md` | Tactical implementer. Reads work order + source. Edits files. Runs lint + tests. Cannot touch git. |
| `agents/a11y-shipper.md` | Pusher. Reads developer's commit. Pushes. Opens a draft PR. Cannot edit source. |

Each gets a separate doc here because each is a worked example of a different design tradeoff.

## Frontmatter — the contract

The investigator's frontmatter (`agents/a11y-investigator.md:1–26`):

```yaml
---
name: a11y-investigator
description: |
    Classify an ADO accessibility bug and produce a complete work order in the bug
    folder. Resolves product, theme, blast radius, cardinal rule, applicable
    knowledge-base rules, and a go/no-go decision. Use when user wants to investigate
    a bug before implementation, or as part of the /a11y-fix workflow. Does NOT edit
    source code or open a browser.
allowed-tools:
    - Read
    - Grep
    - Glob
    - Write
    - Bash
    - mcp__azure-devops__*
    - mcp__github__*
skills: []
model: opus
effort: high
initialPrompt: |
    Phase 0: Your FIRST tool call MUST be Read
    ${CLAUDE_PLUGIN_ROOT}/knowledge/investigator-field-template.md
    — that file is your EXACT output contract. You write ONLY fields listed there.
    After reading the template, read <RUN_DIR>/run-state.json (or initialize if new),
    then follow the 9-phase flow.
---
```

Field by field:

| Field | What it does |
| --- | --- |
| `name` | The identifier passed as `subagent_type` to the `Agent` tool — e.g., `a11y:a11y-investigator` (plugin name + this name). |
| `description` | Two purposes: (1) shown in `/agents` and the footer, (2) seen by Claude when *another* agent or skill considers calling it, so it's keyword-rich and explicit about non-goals. |
| `allowed-tools` | Hard ceiling. Claude Code refuses tool calls outside this list, regardless of what the system prompt says. |
| `skills` | Skills auto-loaded into the agent's context. Empty here — the investigator doesn't need any. |
| `model` | `opus` for high-effort reasoning tasks. The plugin uses Opus for all three; lighter agents can use `sonnet` or `haiku`. |
| `effort` | Roughly thinking budget. `high` for the heavy reasoners. |
| `initialPrompt` | Pre-canned first-user-turn message injected at agent start. The plugin uses it to enforce the mandatory-first-action read (more on that below). |

### `description` doubles as a guardrail

Note the closing line of the investigator's `description`:

> Does NOT edit source code or open a browser.

That's not just for the user — it's seen by the LLM when its parent considers spawning it. A parent agent looking for "a thing that can edit source" reads the description, sees the disclaimer, and looks elsewhere. Use the `description` to advertise non-goals as well as goals.

The developer's description does the same (`agents/a11y-developer.md:3–10`):

> ```
> Autonomous worker. Reads the investigator's work order from `<RUN_DIR>/run-state.json`,
> applies an accessibility fix end-to-end (source edit + regression test when the change
> has behavior worth asserting), runs a self-check against the attachment's expected
> change, writes one final state record, and returns. Does NOT call AskUserQuestion.
> Does NOT create branches, stage, commit, or push. The slash command (`/a11y:developer`)
> owns user gating and the git lifecycle (branch creation up front, diff review on
> return, restore-and-discard on rejection).
> ```

Three "Does NOT" statements. Three things the LLM might be tempted to do that this agent must not. Naming them in the description is the cheapest way to keep them out.

## Tool grants are domain boundaries

The three agents have different `allowed-tools` lists. The differences *are* the architecture:

| Tool | Investigator | Developer | Shipper |
| --- | :-: | :-: | :-: |
| `Read` | ✓ | ✓ | ✓ |
| `Grep` | ✓ | ✓ | ✗ |
| `Glob` | ✓ | ✓ | ✗ |
| `Edit` | ✗ | ✓ | ✗ |
| `Write` | ✓ | ✓ | ✓ |
| `Bash` | ✓ | ✓ | ✓ |
| `mcp__azure-devops__*` | ✓ | ✗ | ✗ |
| `mcp__github__*` | ✓ | ✓ (search) | ✗ |
| `mcp__Ask_Saffron_MCP_Server__*` | ✗ | ✓ | ✗ |
| `mcp__plugin_a11y_playwright__*` | ✗ | ✗ | ✗ |
| `AskUserQuestion` | ✗ | ✗ | ✗ |

Read the table column-by-column:

- **Investigator** can read ADO, GitHub, the filesystem; can write `run-state.json`; can run shell (e.g., `az rest` for attachment downloads). Cannot `Edit` source files. Cannot call any browser MCP. Cannot touch Saffron.
- **Developer** is the only agent with `Edit`. Can call Saffron MCP for design tokens. Can search GitHub for prior art. Cannot read ADO directly (gets bug context from `run-state.json`). Cannot drive a browser.
- **Shipper** is minimal. Can `Read`, `Write`, and shell. No MCP servers — it uses `gh` and `git` CLI directly via Bash.

None of them have `AskUserQuestion`. That's the line dividing "agent" from "slash command" in this architecture, and it's enforced at the tool-grant level. A subagent that *tried* to call `AskUserQuestion` would be denied by the harness.

The investigator's guardrails make the boundary explicit (`agents/a11y-investigator.md:50`):

> **NEVER:** Grep or Glob against the active source tree. You are a **strategic** locator. Tactical source reading is the developer's job.

The developer's guardrails likewise (`agents/a11y-developer.md:554`):

> **NEVER:** `git checkout -b`, `git add`, `git commit`, `git push`, `git stash`, `git restore`, `git branch -D`. The slash command and the shipper own all git mutations. You only `Edit` and `Write` source files.

Two layers of defense: the tool grant says "you can't," and the system prompt says "you wouldn't even if you could." Belt and suspenders.

## The mandatory-first-action read

Every agent in this plugin enforces a non-negotiable rule: **the first tool call must be a Read of the agent's output contract.**

Investigator (`agents/a11y-investigator.md:108–112`):

> Your very first tool call — before anything else — MUST be:
> ```
> Read ${CLAUDE_PLUGIN_ROOT}/knowledge/investigator-field-template.md
> ```

Developer (`agents/a11y-developer.md:79–86`):

> Your very first action MUST be a parallel batch of TWO Reads in one message:
> ```
> Read ${CLAUDE_PLUGIN_ROOT}/knowledge/developer-field-template.md
> Read ${CLAUDE_PLUGIN_ROOT}/knowledge/principles.md
> ```

Shipper (`agents/a11y-shipper.md:36`):

> `Read <RUN_DIR>/run-state.json` as your first action. If missing, return `"Shipper failed. No run-state at <RUN_DIR>."` and stop.

Why insist on this?

1. **The output contract is editable.** The agent's output schema lives as a markdown file in `knowledge/`. Editing the markdown changes the schema, without editing the agent. But that only works if the agent reads the file *every run*, not from cached training memory.
2. **It catches misconfiguration cheaply.** If the cache is broken, the file is missing, or the path resolution failed, the agent sees the failure on its first tool call and can refuse cleanly. (Investigator: "Write a minimal state with `decision.status = 'blocked'`, `runMeta.phase = 'failed'`, return.")
3. **It primes the agent's working context.** The schema is part of the agent's reasoning frame for the rest of the run. Every subsequent decision gets cross-checked against it.

The pattern is "make the contract part of the runtime, not part of the prompt." Doc 09 lists it as pattern 4 (Mandatory-first-action preflight reads).

## Atomic single-write at end

Each agent does **one** `Write` of `run-state.json`, at the very end. Not per-step, not per-phase, not "checkpoint every five minutes."

Developer (`agents/a11y-developer.md:469–488`):

> ## Step 7 — Final write (ONE atomic Write)
>
> This is the ONLY persistence call you make. Do NOT use `Edit` on `run-state.json`. Use `Write`.
>
> 1. `Read <RUN_DIR>/run-state.json`.
> 2. Construct the full updated state in working memory.
> 3. **`Write <RUN_DIR>/run-state.json` with the full new content.** ONE call.

Shipper (`agents/a11y-shipper.md:128–138`):

> ## Step 4 — Final write (ONE atomic Write)
> This is the ONLY persistence call you make. Do NOT use `Edit` on `run-state.json`.
>
> 1. Read current `<RUN_DIR>/run-state.json`.
> 2. Set `shipping.*` per §Schema with terminal status.
> 3. Update top-level `runMeta.phase` ...
> 4. Preserve every other top-level key EXACTLY.
> 5. `Write` the file.

Why this matters is in doc 03 (state machine). The agent design just enforces it — repeatedly, in the system prompt and the guardrails.

## Structured refusals

A "refusal" in this plugin is *not* an unrecoverable failure. It's a deliberate, structured stop. The developer agent has exactly four refusal categories (`agents/a11y-developer.md:512–525`):

> | Trigger | Category | Reason template |
> | --- | --- | --- |
> | Phase precondition fails (Step 1b) | `needs-manual` | "Entry phase=`<actual>`, expected `ready-for-developer`." |
> | `decision.status != "ready-to-proceed"` | `needs-manual` | "Investigator status=`<actual>` (`<gateReason>`)." |
> | Saffron `improvise` for a color value (Step 3e) | `needs-external` | "Design team confirmation required for unresolved color(s)." |
> | Discovery budget exhausted without convergence (3b) | `needs-manual` | "Could not converge on fix target within 15-call budget." |
> | Knowledge file flags cross-repo location | `needs-cross` | "Bug origin in `<other-repo>` per `<knowledge-file>`." |
> | Architectural change required beyond simple a11y fix | `needs-refactor` | "Fix requires `<short>` — out of scope for attribute-level." |

The four categories — `needs-manual`, `needs-external`, `needs-cross`, `needs-refactor` — are an enum the orchestrator branches on. A `needs-external` refusal means "design team must confirm a color." A `needs-cross` means "this bug actually belongs in a different repo." Different categories suggest different recovery actions; structuring them up front means downstream tooling can handle each appropriately.

The investigator has its own four-element gate-reason enum (`agents/a11y-investigator.md:268–275`):

> If `needs-user-clarification`, set `decision.gateReason` to exactly one of:
>
> - `cannot-resolve-product`
> - `theme-ambiguous`
> - `attachment-contradicts-ado`
> - `wcag-not-specified`
>
> Any other `gateReason` value is a bug.

Both agents make the same architectural choice: **finite enums**, not free-form strings. Free text describes the case (`refusal.reason`), but the enum (`refusal.category` / `decision.gateReason`) is what code can branch on.

## Error budgets

Open-ended discovery loops are a known LLM failure mode — "let me grep one more time" until you've spent your context window finding nothing. The developer agent caps its discovery work at 15 tool calls (`agents/a11y-developer.md:251–264`):

> ### 3b. Fallback grep flow (BUDGETED — used when `targetFiles[]` empty or contradicted)
>
> Hard cap: **15 tool calls** total (Greps + Reads). Drill down once you have ≥2 hits in the same area.
>
> [...]
>
> If budget hits 15 without convergence: `Write` at Step 7 with `development.status = "refused"`, `refusal = { category: "needs-manual", reason: "could not converge on fix target within 15-call budget" }`. Do NOT proceed to Step 4 with a guess.

The number is small enough that 15 calls genuinely should be sufficient for a well-scoped bug, and the cap forces clean refusal rather than escalating cost. The agent also dedupes: every Grep is logged in `sourceDiscovery.queriesRun[]` and re-issuing the same `pattern + scopedTo` is forbidden (`agents/a11y-developer.md:565`):

> Re-issue an identical Grep or Read. Check `sourceDiscovery.queriesRun[]` / `filesRead[]` first.

Together: a hard ceiling, structured logging, and dedup-before-dispatch. Doc 09 lists this as pattern 9 (Error budget on discovery).

## Screenshots over text

The developer agent has explicit instructions on visual ground truth (`agents/a11y-developer.md:118–146`):

> ### 1d. Review screenshots — visual ground truth (MANDATORY when present)
>
> The investigator already downloaded each attachment to **`<RUN_DIR>/attachments/`** [...]. Your job here is to **read the images yourself** and corroborate the investigator's `attachments[].analysis.*` with what's actually visible. The investigator's text is a hint; the image is ground truth.
>
> [...]
>
> 3. **If the visual contradicts the analysis**, record in `investigatorOverrides[]`:
>    ```yaml
>    - field: 'attachments[<i>].analysis.<field>'
>      expected: '<what investigator said>'
>      actual: '<what visual shows>'
>      why: '<1 sentence>'
>    ```
>    Trust the visual, not the text.

This is a pattern: when two signal sources disagree, name which wins, and write the resolution into state for audit. The investigator's `attachments[].analysis.*` is text, the screenshot is pixels — pixels win — but the disagreement is preserved as `investigatorOverrides[]` so a human can later catch a systematic issue with the investigator's image-reading.

## "Never guess" — the confidence rule

The investigator scores each classification dimension as Strong / Weak / None and combines them into a High / Medium / Low confidence rating. Then (`agents/a11y-investigator.md:250–252`):

> **Never guess.** If a dimension is Low confidence, gate to the user. Do NOT pick a value and report Medium. This is a hard rule — it is the single biggest v1 failure mode we are eliminating.

The "single biggest v1 failure mode" is silent confidence inflation: an agent that doesn't know but reports confidence anyway, ending up *Medium* when the right answer would have been *Low → ask the user*. The fix isn't to make the model better at guessing; it's to make "I don't know" a structured output and route it to a user gate.

The developer's `improvise` Saffron level is the same idea on the design-system axis (`agents/a11y-developer.md:205–209`):

> **Resolution chain — `consulted.saffron.level` records the LAST step reached:**
>
> 1. **`mcp`** — Saffron returned an actionable component, attribute contract, or equivalent.
> 2. **`grep`** — MCP returned nothing actionable. Grep the active source tree for how peer components in the same theme handle the same WCAG concern. Requires ≥1 clear established usage.
> 3. **`improvise`** — Neither MCP nor grep yielded a pattern. Apply standard a11y practice. Leave a code comment at the implementation point [...]. Add to `additionalNotes[]`.

`improvise` is never a quiet fallback. The agent must add a code comment **and** a note in `additionalNotes[]`. For *colour* values, `improvise` is *forbidden* — the agent refuses with `needs-external` instead of guessing a hex value (`agents/a11y-developer.md:520`).

## Idempotency

Two examples. Developer (`agents/a11y-developer.md:389`):

> **Idempotency** — BEFORE editing, search for the change you're about to make. If already partially present, do NOT layer — record in `adaptations[]` and skip.

Shipper (`agents/a11y-shipper.md:59–65`):

> **Idempotency.** Check if a PR already exists for this branch:
>
> ```bash
> gh pr list --head "<branch>" --state open --json number,url,title
> ```
>
> If a PR exists: write `shipping = { status: 'already-shipped', pullRequest: { number, url, isDraft: <bool> } }`, set `runMeta.phase = 'done'`, return without touching git.

Both are check-then-act: read the world, see if the work is already done, write a different terminal status if so. The shipper's idempotency check has a specific design choice — it checks BEFORE setting `runMeta.phase = "shipping"`, so an already-shipped run never enters the `shipping` phase, which means re-running `/a11y:ship <id>` against a finished bug is always cheap and never causes a phase-lock issue.

## A subtle pattern: "describe, let the system prescribe"

The Saffron resolution chain has a subtler discipline than just "call MCP first." From `agents/a11y-developer.md:203`:

> **Direction matters.** Describe the failing element, the WCAG constraint, and the brand intent — let Saffron prescribe. Never pre-compute values and ask MCP to confirm.

Pre-computing the value and asking the MCP to confirm makes the MCP a yes-machine. Describing the constraint and asking the MCP to prescribe makes it an oracle. The latter catches mistakes; the former hides them.

The same point appears in the reverse-lookup section (`agents/a11y-developer.md:309`):

> REVERSE-LOOKUP — pass values you found in source reads, never values you computed yourself.

`get-saffron-tokens` is for "I found `#212223` in this file — what Saffron token is that?" not for "I think the answer should be a dark gray; here's `#222`, is that a token?" The first is grounded in code; the second is grounded in the agent's bias.

## Anti-patterns: what NOT to put in an agent prompt

The developer's guardrails section is a long enumerated list (`agents/a11y-developer.md:541–584`). Some entries are domain-specific (no inline `style={}`, no English string literals — use the i18n API), but several are *generally* applicable to any agent design:

> 1. Call `AskUserQuestion`. The slash command owns user gating.
> 5. Silently deviate from `approach.filesToChange[]` — record off-plan edits in `adaptations[]` with reason.
> 11. Chain to the verifier — return cleanly and stop.
> 13. Touch investigator-owned fields (`bug.*`, `attachments.*`, `classification.*`, `decision.*`, etc.) — see `developer-field-template.md` Part 4 FORBIDDEN FIELDS.
> 14. Write any field outside `developer-field-template.md` Part 3.
> 15. Use `Edit` on `run-state.json`. Step 7 is ONE atomic `Write` of the full file.
> 16. Re-issue an identical Grep or Read. Check `sourceDiscovery.queriesRun[]` / `filesRead[]` first.

If you're writing your own agent, this is a useful checklist of failure modes to design against:

- Don't reach across boundaries (1, 13, 14).
- Don't silently improvise — log it (5).
- Don't chain to the next step — your job ends, the orchestrator decides what's next (11).
- Don't write the same file more than once per run (15).
- Don't repeat an expensive call (16).

Doc 09 generalises these as patterns 3, 5, 7, 16, 17, and others.

## Checklist: designing a subagent

If you're authoring `your-plugin/agents/<name>.md`, here's the checklist:

1. **Frontmatter**
   - [ ] `name` matches the file (or set explicitly).
   - [ ] `description` says what it does AND what it does NOT do.
   - [ ] `allowed-tools` is the smallest set that lets the agent finish its job.
   - [ ] `model` is justified — `opus` for heavy reasoning, `sonnet`/`haiku` for narrow tasks.
   - [ ] `initialPrompt` enforces the mandatory-first-action read of your output contract.

2. **System prompt body**
   - [ ] States the **role** in 1–2 sentences. What this agent does. What it doesn't.
   - [ ] Names the **inputs** (files it reads, MCP tools it uses).
   - [ ] Names the **output contract** — point at a markdown file the agent reads, don't embed the schema in the prompt.
   - [ ] Walks the **steps** in numbered order. Phase 0 / Step 1a is the preflight read.
   - [ ] Defines **terminal states** — success enum, refusal enum, failure path.
   - [ ] Has a **Guardrails** section with NEVER and ALWAYS rules.
   - [ ] Specifies **single atomic write** of state at the end.

3. **Edge cases to design for**
   - [ ] What happens if the input state file is missing or malformed?
   - [ ] What happens if a downstream tool (MCP server, shell command) fails?
   - [ ] What happens if the agent hits its discovery budget?
   - [ ] What happens if the agent's preflight precondition fails?
   - [ ] What happens if the agent encounters a contradiction between two signal sources?

4. **Output schema**
   - [ ] Lives in a separate `knowledge/<agent>-field-template.md` file.
   - [ ] Has a hard rule "Write only fields listed here."
   - [ ] Has a `FORBIDDEN FIELDS` deny-list for upstream payload fields you must drop.
   - [ ] Has an `additionalNotes[]` escape valve for observations outside the schema.

When you're stuck on a design question for any of these, the answer is usually in `agents/a11y-developer.md` — read it as a reference example.
